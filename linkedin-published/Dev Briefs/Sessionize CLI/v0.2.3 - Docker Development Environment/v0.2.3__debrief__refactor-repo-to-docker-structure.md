## Executive Summary

This document describes the refactoring of the `sessionize-cli` fork to use a Docker-based development environment. The goal was to create a safe, isolated, and reproducible setup for running and improving the CLI tool using Claude Code.

---

## Context

### The Original Tool

`sessionize-cli` is a Node.js CLI tool created by [csima](https://github.com/csima/sessionize-cli) for Sessionize conference organizers to:
- View and rate session submissions
- Navigate between sessions
- Search speakers
- Output JSON for scripting/automation

The tool uses **Browserbase** for cloud browser automation since Sessionize doesn't provide a public API for organizers.

### The Problem

Running AI-assisted development tools (like Claude Code) directly on a host machine introduces risks:
- System modification by AI agents
- State pollution from experiments
- Reproducibility issues ("works on my machine")
- Security concerns with AI having system access

### The Solution

Containerize the development environment using Docker, following patterns established in the [claude-flow CRM project](https://github.com/the-cyber-boardroom/claude-flow__create-crm-mvp).

### Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Non-root user `claude` | Security: limits container capabilities |
| Volume-mounted `workspace/` | Code changes persist and are git-tracked on host |
| Separate `/home/claude/deps/` | Dependencies baked into image, not synced to host |
| Named volume for node_modules | Masks bind mount, avoids performance overhead |
| No API key in image | Claude Code authenticates via MAX account interactively |

## Challenges and Solutions

### Challenge 1: node_modules Syncing to Host

**Problem:** When running `npm install` inside the container with a bind-mounted workspace, `node_modules/` syncs back to the host. This causes:
- Performance overhead (thousands of small files)
- Cluttered local directory
- Unnecessary git tracking concerns

**Solution:** Use a named volume to mask the node_modules directory:
```yaml
volumes:
  - ./workspace:/home/claude/workspace
  - sessionize_node_modules:/home/claude/workspace/node_modules

volumes:
  sessionize_node_modules:
```

The named volume overlays that specific path, keeping node_modules container-only.

---

### Challenge 2: npm install During Build vs Runtime

**Problem:** We want `sessionize` to work immediately without manual setup. But the code comes via volume mount at runtime, so we can't run `npm install` during build.

**Initial Attempt:** Use an entrypoint script to install on first run.

**Better Solution:** Copy `package*.json` and source to a separate location (`/home/claude/deps/`) during build:
```dockerfile
COPY --chown=claude:claude workspace/package*.json /home/claude/deps/
WORKDIR /home/claude/deps
RUN npm install

COPY --chown=claude:claude workspace/bin/ /home/claude/deps/bin/
COPY --chown=claude:claude workspace/lib/ /home/claude/deps/lib/
RUN npm link

ENV NODE_PATH=/home/claude/deps/node_modules
```

This gives us:
- `sessionize` works immediately (from baked-in deps)
- Workspace stays clean (no node_modules)
- Development changes can override via `npm link` in workspace

---

### Challenge 3: npm Global Install Permission Denied

**Problem:** 
```
npm error code EACCES
npm error syscall mkdir
npm error path /usr/local/lib/node_modules/@anthropic-ai
```

**Cause:** `npm config set prefix` was run before switching to the `claude` user, so npm still tried to use the system-wide `/usr/local/lib/node_modules/`.

**Solution:** Ensure `USER claude` comes BEFORE npm configuration:
```dockerfile
# Create non-root user
RUN useradd -m -s /bin/bash claude

# Switch to non-root user FIRST
USER claude

# THEN configure npm for local global installs
RUN mkdir -p /home/claude/.npm-global \
    && npm config set prefix '/home/claude/.npm-global'

ENV PATH="/home/claude/.npm-global/bin:${PATH}"

# NOW install global packages
RUN npm install -g @anthropic-ai/claude-code
```

---

### Challenge 4: Credential Management

**Problem:** The CLI requires Browserbase API keys and Sessionize credentials. These shouldn't be baked into the image or committed to git.

**Solution:** Create config file manually inside container:
```bash
cat > ~/.sessionize-cli.json << 'EOF'
{
  "apiKey": "bb_live_xxxxx",
  "projectId": "your-project-id",
  "email": "your@email.com",
  "password": "your-password",
  "eventId": "12345",
  "evaluationId": "6789"
}
EOF
chmod 600 ~/.sessionize-cli.json
```

**Alternative:** Mount a config file via docker-compose:
```yaml
volumes:
  - ./data/sessionize-cli.json:/home/claude/.sessionize-cli.json
```

## The Why, How, and What

### WHY: Motivation for Docker-based Development

1. **Safety** - AI agents (Claude Code) can modify files, run commands, install packages. Containing this in Docker prevents unintended host system changes.

2. **Reproducibility** - Anyone can clone the repo, run `docker compose up`, and have an identical environment. No "works on my machine" issues.

3. **Ephemerality** - Easy to reset: `docker compose down -v` wipes everything. Start fresh anytime.

4. **Separation of Concerns** - Git tracking happens on host. Container is git-unaware. Clean mental model.

5. **Claude Code Integration** - Provides isolated sandbox for AI-assisted development with MAX account authentication.

### HOW: Implementation Approach

1. **Started with proven pattern** - Based on the claude-flow CRM project's Docker setup.

2. **Iterative refinement** - Each challenge (node_modules sync, build vs runtime, permissions) was addressed incrementally.

3. **Preserved development workflow** - Volume mounts ensure code changes persist. Named volumes handle the node_modules issue.

4. **Baked dependencies into image** - Copied package.json and source to separate location for immediate usability.

### WHAT: Final Deliverables

| File | Purpose |
|------|---------|
| `Dockerfile` | Container definition with Claude Code and sessionize-cli |
| `docker-compose.yml` | Orchestration with volume mounts |
| `README.md` | Quick start and usage documentation |
| `workspace/` | Git-tracked source code (volume-mounted) |
| `data/` | Git-ignored persistent data |

## Usage Summary

### First Time Setup
```bash
# Build and start
docker compose up --build -d

# Enter container
docker exec -it sessionize-cli bash

# Configure credentials
cat > ~/.sessionize-cli.json << 'EOF'
{
  "apiKey": "bb_live_xxxxx",
  "projectId": "your-project-id",
  "email": "your@email.com",
  "password": "your-password",
  "eventId": "12345",
  "evaluationId": "6789"
}
EOF

# Test
sessionize session show
```

### Development with Claude Code
```bash
docker exec -it sessionize-cli bash
npx claude
```

### Running Commands Directly
```bash
docker compose exec sessionize-cli sessionize session list
```

## Lessons Learned

1. **Order matters in Dockerfile** - USER must come before npm config for prefix to work.

2. **Named volumes are powerful** - They can mask specific subdirectories of bind mounts.

3. **Separate deps from workspace** - Baking dependencies into a separate path enables immediate usability while keeping workspace clean.

4. **Don't over-engineer credentials** - Manual creation inside container is simple and secure enough for development.

5. **Follow established patterns** - The claude-flow CRM project provided a proven foundation to build upon.
