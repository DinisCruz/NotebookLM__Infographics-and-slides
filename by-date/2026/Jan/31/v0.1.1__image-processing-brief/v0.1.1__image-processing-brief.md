# Project Brief

## Serverless, Stateless Image Processing Service (AWS + Marketplace)

---

## 1. Purpose & Motivation

This project aims to create a **standalone, serverless, ephemeral, and stateless image processing service** deployed on AWS and suitable for **distribution via the AWS Marketplace**.

The service is motivated by a real, immediate need:
supporting **attachments in a Git-backed, graph-based issue tracking system**, where images must be:

* Uploaded as attachments
* Transformed or compressed
* Possibly resized or reformatted
* Returned in a predictable, structured way

Rather than embedding image processing logic (and heavy dependencies like Pillow/PIL) into multiple projects, this service **isolates image manipulation into a single-purpose microservice** that can be reused across systems and sold independently.

---

## 2. Core Design Principles

The service is intentionally designed to be:

* **Stateless**
  No data persisted between requests. Each request is self-contained.

* **Ephemeral**
  No reliance on local disk or cache. Results are returned immediately.

* **Serverless-first**
  Primary deployment target is AWS Lambda, with optional EC2/AMI packaging for Marketplace distribution.

* **Single responsibility**
  One job: *image in → transformation → image (or metadata) out*.

* **Dependency isolation**
  Heavy libraries (e.g. Pillow) live **only** inside this service.

* **Type-safe and schema-driven**
  No raw strings. All inputs/outputs use explicit schemas and type-safe primitives.

* **Composable & reusable**
  Designed to be consumed by:

  * other backend services
  * CLI tools
  * automation pipelines
  * future UIs

---

## 3. High-Level Architecture

### 3.1 Logical Flow

```
Client (Python SDK / Service)
        │
        │  HTTP (REST)
        ▼
FastAPI Image Service
        │
        │  Pillow / Image Ops
        ▼
Image / Metadata Response
```

There is:

* **no database**
* **no cache**
* **no shared state**

---

### 3.2 Deployment Targets

The same codebase supports multiple deployment modes:

1. **AWS Lambda**

   * Primary runtime
   * Stateless, scalable
   * Ideal for bursty image workloads

2. **EC2 → AMI**

   * Built via CI
   * Used for AWS Marketplace listings
   * Allows users to deploy as managed compute

3. **(Future)** Container / Kubernetes

   * Optional, but architecture allows it

## 4. Repository Structure

To enforce schema consistency and clean separation of concerns, the project uses **two repositories**.

---

### 4.1 Repository 1: Image Processing Service (FastAPI)

**Purpose**
Hosts the actual image processing logic and REST API.

**Responsibilities**

* Import and use **Pillow (PIL)** and any image libraries
* Define REST endpoints
* Validate input schemas
* Execute transformations
* Return transformed images or metadata
* Host Swagger/OpenAPI UI
* Serve a minimal web UI (for manual testing)

**Key characteristics**

* This is the *only* repo allowed to import Pillow
* Uses `type_safe` primitives (from osbot utils)
* Depends on the client repo for schemas

---

### 4.2 Repository 2: Client SDK (Python)

**Purpose**
Provide a **type-safe Python client** for calling the image service.

**Responsibilities**

* Define all request/response schemas
* Provide typed client methods (no raw HTTP calls)
* Encapsulate API paths and payload formats
* Act as the *single source of truth* for schemas

**Key architectural rule**

> Server depends on client schemas
> Client does **not** depend on FastAPI

This guarantees:

* Client and server always share identical schemas
* No schema drift
* Strong compile-time and runtime guarantees

---

## 5. Schema & Type Safety Strategy

### 5.1 Type-Safe Design

* No raw strings for:

  * operations
  * formats
  * options
* All parameters expressed as:

  * enums
  * typed objects
  * constrained values

This improves:

* correctness
* security
* maintainability
* refactor safety

---

### 5.2 Schema Ownership

* **Client repo owns schemas**
* Schemas include:

  * image input descriptors
  * transformation requests
  * transformation results
  * error models

FastAPI:

* imports schemas
* uses them directly in route definitions

---

## 6. Functional Scope (Initial Version)

The service intentionally starts **small but valuable**.

### 6.1 Core Operations

Each request performs **one logical transformation**.

#### Image In → Image Out

* Resize (width, height, aspect modes)
* Format conversion (PNG, JPEG, WEBP)
* Compression / quality adjustment
* Orientation normalization (EXIF)
* Thumbnail generation

#### Image In → Metadata Out

* Dimensions
* File size
* Format
* Color mode
* EXIF summary (optional)

#### (Optional / Future)

* Text → Image (simple rendering)
* Image → Text (OCR, later)
* Image → Hash / Fingerprint

---

### 6.2 REST API Shape (Conceptual)

```
POST /image/transform
POST /image/compress
POST /image/resize
POST /image/metadata
```

Each endpoint:

* Accepts a typed request
* Returns a typed response
* Can accept image via:

  * multipart upload
  * base64 (explicit, typed)
  * URL (future)

## 7. UI Strategy (Phase 1)

For simplicity and speed:

* UI is embedded in the **FastAPI service**
* Same process serves:

  * Swagger/OpenAPI
  * Simple HTML/JS UI for manual testing

Benefits:

* Zero extra deployment
* Easy to demo
* Great for early adopters and testing

A separate UI repo can be introduced later if needed.

### 8.1 CI Responsibilities

3. Deploy Lambda function
4. Build EC2 image
