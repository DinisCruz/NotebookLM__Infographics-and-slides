## Executive Summary

We've built a **graph-based issue tracking system that lives inside your Git repository**, eliminating external dependencies, authentication complexity, and vendor lock-in. Issues, tasks, relationships, and activity logs are stored as JSON files alongside your code—committed, versioned, and portable.

This isn't just another issue tracker. It's **infrastructure for AI agent collaboration**.

When AI agents like Claude Code work on your codebase, they need a way to track tasks, report progress, and coordinate with humans and other agents. Traditional solutions (GitHub Issues, Jira, Linear) introduce:

- **Authentication complexity** — Service accounts, API tokens, OAuth flows
- **Vendor lock-in** — Your issue history trapped in proprietary databases
- **Network dependencies** — Agents need internet access to update status
- **Rate limiting** — API quotas throttle agent productivity
- **Integration friction** — Every tool needs its own connector

Our solution: **Make the repository itself the source of truth.**

### Graph Data Model

Unlike flat issue lists, we use a **graph model** where everything is a node and relationships are first-class:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           GRAPH DATA MODEL                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   NODES (Entities)                    LINKS (Relationships)                 │
│   ════════════════                    ═════════════════════                 │
│                                                                             │
│   • Bug      (defects)                • blocks / blocked-by                 │
│   • Task     (work units)             • has-task / task-of                  │
│   • Feature  (capabilities)           • assigned-to / assignee-of           │
│   • Person   (humans & agents)        • depends-on / dependency-of          │
│                                       • relates-to (symmetric)              │
│                                                                             │
│   Example Graph:                                                            │
│   ──────────────                                                            │
│                                                                             │
│                         ┌─────────────────┐                                 │

│                         │ Authentication  │                                 │
│                         └────────┬────────┘                                 │

│              ┌───────────────────┼───────────────────┐                      │
```

## How It Works: File Storage in Git

### Directory Structure

Issues are stored in `.issues/` at your repository root:

```
.issues/
├── _index.json                          # Global stats & counts
├── config/
│   ├── node-types.json                  # Type definitions (Bug, Task, etc.)
│   ├── link-types.json                  # Relationship definitions
│   └── settings.json                    # Global settings
└── data/
    ├── bug/
    │   ├── _index.json                  # Bug-specific index
    │   ├── Bug-1/
    │   │   ├── node.json                # Issue data
    │   │   └── attachments/
    │   │       └── screenshot.png
    │   └── Bug-2/
    │       └── node.json
    ├── task/
    │   ├── _index.json
    │   ├── Task-1/
    │   │   └── node.json
    │   └── Task-2/
    │       └── node.json
    ├── feature/
    │   └── Feature-1/
    │       └── node.json
    └── person/
        ├── Person-1/
        │   └── node.json                # Human: Alice
        └── Person-2/
            └── node.json                # Agent: Claude
```

### Node File Format

Each `node.json` is a self-contained, human-readable document:

```json

  "node_type": "bug",
  "node_index": 27,
  "label": "Bug-27",

  "description": "Users cannot log in when their password contains & or < characters.\nThe server returns HTTP 500 with message 'XML parsing failed'.",
  "status": "in-progress",
  "tags": ["auth", "security", "urgent"],
  "properties": {
    "severity": "high",
    "browser": "Chrome 120",
    "reported_by": "customer-support"
  },
  "links": [
    {
      "link_type_id": "lt_001",
      "verb": "blocks",
      "target_id": "x9y8z7w6v5",
      "target_label": "Task-15",
```

### Backend Selection

```python
from graph_services import Graph__Repository__Factory

# For unit tests - instant, no cleanup
repo = Graph__Repository__Factory.create_memory()

# For development - Git tracked
repo = Graph__Repository__Factory.create_local_disk(
    root_path='/path/to/repo'
)

# For embedded/desktop apps - single file database
repo = Graph__Repository__Factory.create_sqlite(
    db_path='/data/issues.db'
)

# For export/transfer - compressed archive
repo = Graph__Repository__Factory.create_zip(
    zip_path='/backups/issues-2026-01-31.zip'
)

# For enterprise - cloud storage
repo = Graph__Repository__Factory.create_s3(
    bucket='company-issues',
    prefix='project-alpha/'
)
```

### Example: Agent Creates and Links Issues

```bash
# Agent discovers a bug while working on a task
curl -X POST http://localhost:8000/api/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "node_type": "bug",
    "title": "SQL injection vulnerability in user search",
    "description": "The /api/users/search endpoint does not sanitize the query parameter.",
    "tags": ["security", "critical"],
    "properties": {
      "severity": "critical",
      "cve": "pending",
      "discovered_by": "claude-code-agent"
    }
  }'

# Response
{
  "success": true,
  "node": {
    "label": "Bug-28",
    "node_type": "bug",
    "title": "SQL injection vulnerability in user search",
    "status": "backlog",
    ...
  }
}

# Agent links the bug to the task it was working on
curl -X POST http://localhost:8000/api/nodes/Bug-28/links \
  -H "Content-Type: application/json" \
  -d '{
    "verb": "blocks",
    "target_label": "Task-15"
  }'

# Response shows bidirectional link created
{
  "success": true,
  "source_link": {"verb": "blocks", "target_label": "Task-15"},
  "target_link": {"verb": "blocked-by", "target_label": "Bug-28"}
}

# Agent assigns the bug to a human for security review
curl -X POST http://localhost:8000/api/nodes/Bug-28/links \
  -H "Content-Type: application/json" \
  -d '{
    "verb": "assigned-to",
    "target_label": "Person-1"
  }'
```

## The Filesystem-as-Database Philosophy

This project extends a development philosophy: **use the filesystem as your database**.

### Traditional vs. Filesystem Approach

```
┌─────────────────────────────────────────────────────────────────────────────┐
│               TRADITIONAL DATABASE VS. FILESYSTEM DATABASE                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  TRADITIONAL:                                                               │
│  ────────────                                                               │
│                                                                             │
│   Application ──▶ ORM ──▶ Database Server ──▶ Disk                         │
│                          (PostgreSQL, MySQL)                                │
│                                                                             │
│   • Requires running server                                                 │
│   • Connection management                                                   │
│   • Schema migrations                                                       │
│   • Backup complexity                                                       │
│   • Scaling concerns                                                        │
│   • Vendor-specific SQL                                                     │
│                                                                             │
│  FILESYSTEM:                                                                │
│  ───────────                                                                │
│                                                                             │
│   Application ──▶ Memory-FS ──▶ Storage Backend                            │
│                                 (Files, S3, Git)                            │
│                                                                             │
│   • No server required                                                      │
│   • Files are the schema                                                    │
│   • Backup = copy files                                                     │
│   • Git = version control                                                   │
│   • Cloud storage = infinite scale                                          │
│   • Human-readable JSON                                                     │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  WHEN FILESYSTEM WORKS BETTER:                                              │
│  ─────────────────────────────                                              │
│                                                                             │
│  ✓ Document-oriented data (issues, configs, logs)                          │
│  ✓ Write-occasionally, read-often patterns                                 │
│  ✓ Need versioning/history (Git gives this free)                           │
│  ✓ Human-readable/editable data                                            │
│  ✓ Offline-first requirements                                              │
│  ✓ Avoiding infrastructure dependencies                                    │
│                                                                             │
│  WHEN TRADITIONAL DB WORKS BETTER:                                          │
│  ─────────────────────────────────                                          │
│                                                                             │
│  ✓ High-frequency transactions                                             │
│  ✓ Complex relational queries                                              │
│  ✓ Multi-user concurrent writes                                            │
│  ✓ ACID requirements                                                       │
│  ✓ Large-scale aggregations                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Quick Start

### 1. Installation

```bash
# Clone the repository with issue tracking built in
git clone https://github.com/your-org/your-repo.git
cd your-repo

# Install dependencies
pip install -r requirements.txt

# Start the API server
python -m uvicorn main:app --reload
```

### 2. Initialize Default Types

```bash
curl -X POST http://localhost:8000/api/types/initialize
```

### 3. Create Your First Issue

```bash
curl -X POST http://localhost:8000/api/nodes \
  -H "Content-Type: application/json" \
  -d '{
    "node_type": "bug",
    "title": "Welcome to Git-native issue tracking!",
    "description": "This is your first issue."
  }'
```

### 4. Commit to Git

```bash
git add .issues/
git commit -m "Initialize issue tracking"
git push
```

## Conclusion

Git-native issue tracking represents a fundamental shift in how we think about project management infrastructure:

1. **Issues are data, not a service.** Store them like any other project artifact.

2. **The filesystem is a database.** With the right abstraction, files + Git provide versioning, backup, and portability that traditional databases struggle to match.

3. **AI agents are first-class citizens.** Design for machine collaboration from the start, not as an afterthought.

4. **Portability matters.** Your issue history shouldn't be trapped in a vendor's database.

5. **Simplicity enables power.** By removing external dependencies, we gained flexibility (multiple backends, offline operation, branch-aware issues) that would be impossible with traditional architectures.

This is more than an issue tracker. It's **infrastructure for the age of AI-assisted development**.
