# Micropayments for Agents: Budget Control, Cost Tracking, and the Billing Graph

**version** v0.1.5  
**date** 11 Feb 2026  

## The Problem

Agents are, by design, over-enthusiastic. They're creative. They keep going. They keep trying things. And as agentic platforms give them more flexibility to run autonomously, that's exactly what you want — until you don't.

Every agent action has a cost. Every LLM invocation costs tokens. Every API call, every page fetched, every file processed, every inter-agent delegation — it all costs something. Even if each action is minimal, they compound. And without visibility and control, agents will happily burn through resources chasing a rabbit hole, or worse, create loops where they keep calling each other indefinitely.

There's also the lazy agent problem: one agent starts offloading work to other agents that it should be doing itself. The librarian gets hammered with requests because every other agent finds it easier to ask than to look things up themselves. That's a resource allocation problem that needs to be visible and controllable.

## The Solution: Micropayments (Nanopayments) for Everything

Introduce a system where every action triggers a micro (or nano) payment. Not real money (at first) — credits, tokens, budget units. The point is to make cost visible and controllable at every level.

### What gets a micropayment

- **Agent-to-agent calls** — when the designer asks the librarian to research something, the designer "pays" from their budget. The caller pays.
- **LLM invocations** — every token consumed
- **Resource access** — reading files, fetching web pages, accessing APIs
- **Website visits** — every page view, every API call from a user or agent
- **Task execution** — every step in a workflow
- **Infrastructure** — Lambda invocations, S3 operations, compute time

Everything. If it consumes a resource, it triggers a payment.

### The caller pays

This is an important principle: when one agent calls another agent or accesses a shared resource, the CALLER pays. The cost flows back to the originator of the work. This means:

- If the historian asks the librarian to do deep research, the historian's budget gets charged for the librarian's work
- If an agent triggers a cascade of sub-tasks, the budget consumption is attributed to the original task
- You can trace the cost of any outcome back to the decision that caused it

This prevents the lazy agent problem — if calling another agent costs you budget, you think twice about whether you really need to.

## Agent Budgets

Every agent, when it starts a task, gets a budget:

- **Token budget** — max LLM tokens for this task
- **Call budget** — max inter-agent calls (e.g. 500 calls)
- **Time budget** — max execution time
- **Cost budget** — max total cost in credits

When the budget runs low, the agent can:

1. Complete what it can within budget
2. Request a budget increase (which requires approval)
3. Report what it couldn't finish and why

This is a great way to project costs in advance. For each task type, we build up historical data: "a typical code review task costs 200 credits." If a task starts consuming 2,000, something is wrong — either the task is bigger than expected, or the agent is in a loop.

### Budget as guardrail

Budgets aren't just cost control — they're quality control. An agent that's burning through budget is probably not being efficient. Constraints force creativity. An agent with unlimited budget will try everything; an agent with a tight budget will try the right things.

## Website Micropayments

Extending the same model to our websites:

- Every visitor gets an identity — either via login or fingerprint-based assignment
- Every visitor gets a budget (anonymous visitors get a default budget, logged-in users get more)
- Every page view, every API call costs a micro-amount from that budget
- When the budget runs out, the visitor hits a gate — log in for more, or wait for the budget to refresh

This gives us:

- **Rate limiting** that's user-aware, not just IP-based
- **Usage visibility** — who's consuming what, how much, how often
- **Abuse prevention** — bots and scrapers burn through budget quickly
- **A path to monetisation** — the budget system IS the billing system, just with virtual credits initially

And because we already have FastAPI behind the scenes, adding this layer is infrastructure work, not a redesign.

## Learning and Optimisation

Over time, the micropayment data becomes incredibly valuable:

- **Expected cost per task type** — what SHOULD a code review cost? What SHOULD a librarian research cost?
- **Anomaly detection** — this task is costing 10x the expected amount. Why?
- **Agent efficiency comparison** — which agents are cost-efficient? Which are wasteful?
- **Workflow optimisation** — which paths through the agent graph are cheapest for the same quality outcome?
- **Budget projections** — for the next iteration, we expect these tasks, so we need this total budget

The graph of expected costs becomes a planning tool. And deviations from expected become flags for investigation.

## The Billing Graph

All of this lives in Issues FS as a graph:

- **Budget nodes** — assigned to agents, users, tasks
- **Payment edges** — connecting actions to costs, callers to callees
- **Accumulation** — rolling totals per agent, per task, per workstream, per iteration
- **History** — cost trends over time, version-controlled like everything else

The billing graph connects to the task graph (what work was done), the agent graph (who did it), and the cost control graph (from the earlier brief). It's all one graph.

## Evolution Path

1. **Phase 1: Tracking only** — instrument everything with cost tracking. Don't enforce budgets yet. Just see where the money goes. (This is the cost control brief, implemented.)
2. **Phase 2: Agent budgets** — assign budgets to agents per task. Soft limits — warn but don't stop. Learn what normal looks like.
3. **Phase 3: Hard limits** — enforce budgets. Agents must operate within constraints or request increases.
4. **Phase 4: Website micropayments** — extend to user-facing systems. Identity, budgets, gates.
5. **Phase 5: Real costs** — connect virtual credits to actual costs (LLM tokens, cloud resources). The billing system becomes real.
6. **Phase 6: External billing** — charge external users/customers. The micropayment infrastructure is already there.

## For the Agents

- **Architect**: design the micropayment schema. What are the node types (budget, payment, balance)? What are the edge types (charges, transfers, allocations)? How does the "caller pays" attribution work in the graph? How does this integrate with the existing cost control design?
- **Dev**: start with Phase 1 — instrument the current agent workflows to log every action with a cost estimate. We need the data before we can set meaningful budgets. Use the Issues FS graph to store the cost events.
- **DevOps**: the website micropayment layer needs identity management. What's the simplest way to assign an identity to every visitor? How do we implement budget-gated access on top of FastAPI?
- **GRC**: micropayments create a financial audit trail. Define what records need to be kept, what reports need to be generated, and how this connects to the risk register (budget overruns as risks).
- **Conductor**: agent budget allocation is a scheduling decision. When you assign a task to an agent, you also assign a budget. Define how budget allocation works in the task assignment workflow.
- **QA**: test the budget enforcement. Can an agent exceed its budget? What happens at the boundary? Test the lazy agent scenario — create a situation where one agent repeatedly delegates to another and verify the cost attribution is correct.
