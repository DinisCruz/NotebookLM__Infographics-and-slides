# Dependency Adaptation: Strategic Copy Over Wholesale Import

**version** v0.1.5  
**date** 11 Feb 2026  

## The Pattern

Instead of importing a third-party library wholesale (and all its transitive dependencies), use an LLM to **strategically copy and adapt** only the specific functionality you actually need.

This isn't dependency elimination. It's dependency transformation — from "import everything, use 5%" to "copy the 5% you need, customise it, maintain just that."

## How It Works

1. **Identify what you actually use** — from a library with 10,000+ lines, you're typically using 5-20% of the functionality
2. **Use the library as reference** — the source code, unit tests, use cases, documentation — it's all input for the LLM
3. **Copy over just the functionality you need** — the LLM creates a plan, extracts the relevant code, adapts it to your codebase patterns (Type_Safe, your schemas, your naming conventions)
4. **Customise it** — the copied code is now yours, already aligned with how you want to use it
5. **Keep it in sync** — LLMs can compare versions between the reference library and your adapted copy, flagging when the upstream changes something relevant

## The Maths

If a library has 10,000 lines and you use 5% of it, you're maintaining 500 lines instead of depending on 10,000 (plus its 20 transitive dependencies, which could be another 100,000 lines). Even at 20% usage, 2,000 lines of your own code is dramatically less surface area than the full dependency tree.

The objection is "but now you have to maintain that code." Yes. But you were already maintaining your dependency — checking for updates, testing compatibility, dealing with breaking changes, auditing for vulnerabilities. You were just doing it for 100,000 lines of code you didn't understand instead of 500 lines you do.

## Why This Works Now (and Didn't Before)

In the past, the cost of rewriting library functionality was prohibitive. You didn't want to reinvent the wheel. The import tax (all those extra dependencies) was worth paying to avoid the rewrite cost.

With LLMs, the rewrite cost has collapsed. You can say: "I want the same functionality as this library's authentication module, adapted to my Type_Safe patterns, with just the features I use." And get it. Then keep it maintained with periodic LLM-assisted comparisons against the upstream.

The economics have flipped: the import tax (dependency tree, attack surface, maintenance burden, breaking changes) now costs more than the adaptation.

## What This ISN'T For

This isn't for everything. For genuinely complex, deeply specialised libraries — cryptography, database drivers, protocol implementations — wholesale import still makes sense. The domain expertise baked into those libraries is too deep to casually replicate.

But for utility libraries, framework wrappers, API clients, data processing helpers, validation libraries — the stuff that makes up the bulk of most dependency trees — strategic adaptation is often better.

## The Security Angle

This dramatically reduces the attack surface:

- **Fewer dependencies** = fewer supply chain attack vectors
- **Less code running** = smaller surface to audit
- **Code you understand** = vulnerabilities you can actually find and fix
- **No transitive surprises** = no "a dependency of a dependency of a dependency had a malicious update"

The classic security question "there's a vulnerability in library X, does it affect us?" becomes much simpler: either we have the affected code (and we can check because it's 500 lines we understand) or we don't (because we never copied that part).

## The Open Source Business Model Opportunity

This pattern opens up an interesting commercial model for open source developers:

### The service: customised dependency adaptation

The original library maintainers are the best people to create adapted versions of their code. They understand the domain deeply. They know which parts are safe to extract and which have hidden dependencies.

So the business model becomes:

- **Open source library** — free, full-featured, traditional import
- **Adaptation service** — paid. The maintainers create a customised, minimal version of their library tailored to YOUR codebase. Just the features you use, adapted to your patterns, maintained on YOUR repo.

This is a much better value proposition than "pay for support on the full library." The customer gets:

- Less code to audit
- Smaller attack surface
- Code that matches their conventions
- No transitive dependency tree
- Updates focused on what they actually use

The maintainer gets:

- A revenue stream beyond donations and sponsorship
- A service that leverages their unique domain expertise
- Work that LLMs can assist with (reducing their effort per customer)
- A model that scales — each adaptation is similar but customised

### The delivery model

The adapted code lives in the customer's repo. It's their code now. The maintainer provides:

- Initial adaptation (one-time)
- Periodic sync when upstream changes matter (subscription)
- Vulnerability response — "does this CVE affect your adapted version?" (included in subscription)

This shifts from "sprawling dependency tree" to "highly focused, maintained injection of exactly what you need."

## Reference Implementations

The way I already work with my own libraries (osbot-utils, osbot-aws, etc.) is a version of this pattern. They serve as reference implementations — a central place where I maintain the canonical version. Then in other projects, I bring in just what I need, adapted to that project's context.

The LLM makes the "bring in and adapt" step fast. And it can keep the adapted versions in sync with the reference by comparing and flagging relevant upstream changes.

## How This Connects to Issues FS

### Dependency tracking as graph
Every adapted dependency becomes a node in the Issues FS graph. It links to: the source library (reference), the specific version/commit it was adapted from, the functions/modules that were copied, the customisations applied. When the upstream changes, the graph shows you exactly what might need updating.

### Vulnerability mapping
When a CVE is published for a library, query the graph: "do we have any adapted code from this library?" → "yes, from version X, these specific functions." → "does the CVE affect those functions?" This is the security review question, answered by graph traversal.

### The agency metric
From the earlier code agency brief: every dependency adapted and brought in-house increases your agency score. Track this over time. Show the shift from "90% of running code is opaque dependencies" to "70% is code we understand and control."

## For the Agents

- **Architect**: define the criteria for "adapt vs import." When is a dependency a candidate for adaptation? When should we keep the full import? Create the decision framework.
- **Dev**: for the next dependency that we'd normally import, try the adaptation pattern instead. Document the process, the time spent, the resulting line count vs the full library.
- **AppSec**: quantify the attack surface reduction. For each adapted dependency: how many lines of code removed from the dependency tree? How many transitive dependencies eliminated? Track this as a security metric.
- **Journalist**: the open source business model angle is a compelling article. "How LLMs change the economics of open source: from import to adaptation." Good for the public website.
- **GRC**: dependency adaptation has compliance implications — we now own (and are responsible for) the adapted code. How does this affect our risk register? Is this a risk reduction (less surface) or risk increase (more code to maintain)? Document the trade-off.
