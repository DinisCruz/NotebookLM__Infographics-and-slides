# Agentic Coding Increases Your Agency Over Code

**version** v0.1.5  
**date** 11 Feb 2026  

## The Counterintuitive Claim

In the hands of a good engineer, agentic coding — Gen AI development, selective vibe coding, LLM-assisted development — actually **increases** the amount of code you understand and have agency over. This goes against a lot of the perceived wisdom that says LLMs are generating code nobody understands.

Let me show why.

## The Code You Actually Control Today

When you ship a Python service, here's the stack of code involved, from most to least understood:

### Layer 1: Your code
Code you wrote. You understand it, you control it. This is the smallest layer by volume but the one you have full agency over.

### Layer 2: Direct dependencies
FastAPI, Pydantic, whatever libraries you import. You have SOME understanding of their behaviour. In Python you can at least read the source. But there's already a massive drop in understanding and control compared to your own code.

### Layer 3: Transitive dependencies
The dependencies of your dependencies. That massive dependency tree that gets pulled into your project. You have much less understanding of this code, though in Python you can still technically read it.

### Layer 4: Binary extensions
Dependencies like pytest that use compiled binary modules. You can't see inside them. You have even less control over what's happening.

### Layer 5: Python runtime / native libraries
The Python standard library — most of which are wrappers around Python executables and C binaries. You could look at some of it, but you're really not going to.

### Layer 6: C libraries
The C code that the Python runtime is built on. You have no visibility into this.

### Layer 7: Processor / assembly
The actual hardware logic, which these days includes software logic on the processor itself. Zero visibility.

### The honest picture

The amount of code you actually understood was always **tiny** compared to the total code running in your application. The amount of code with zero agency was always **massive**. This was true before LLMs. We just didn't talk about it.

## What Agentic Coding Changes

When done right, agentic coding **shifts code from the middle layers into Layer 1 — your codebase**.

Instead of importing a library for something, you write it yourself (with LLM assistance). Instead of depending on a framework's magic, you implement the specific behaviour you need. Instead of a transitive dependency tree you've never read, you have code in your repo that you can read, test, and refactor.

### The vibe coding problem

A lot of people doing vibe coding are making this shift — they're moving code from dependencies into their codebase. The shift is real. But they don't understand the code they've moved in. It's still opaque to them. They traded one kind of opacity (dependency you've never read) for another (generated code you've never read).

### The good engineer difference

In the hands of a good engineer, the shift is different. You:

- Apply engineering practices and refactoring to the generated code
- Ensure visibility — you read it, you understand it, you make it match your standards
- Use well-architected components (Type_Safe, domain types, clean abstractions)
- Actually REDUCE the number of dependencies

So what you end up with is: more code in your repo that you understand and control, fewer dependencies you don't understand and don't control. Your agency over the total codebase has **increased**, not decreased.

## The Dependency Reduction Pattern

This is what I actually do in practice. In Python, I tend to use just the Python native libraries. In JavaScript, I use pure JavaScript and HTML. The goal is to minimise the code I don't have agency over.

Agentic coding accelerates this because it makes it feasible to write things yourself that previously you would have pulled in a library for. The LLM handles the boilerplate, you handle the architecture and quality. The result: fewer dependencies, more control, smaller attack surface, fewer surprises.

The maths: if I remove a dependency that had 50 transitive sub-dependencies and replace it with 200 lines of my own code that I understand and test — I've dramatically increased my agency over the running system, even though I "wrote more code."

## The Agency Stack (Revised)

With agentic coding done well:

| Layer | Before | After |
|-------|--------|-------|
| Your code | Small | **Much larger** — absorbed functionality from dependencies |
| Direct dependencies | Many | **Fewer** — replaced where feasible |
| Transitive dependencies | Massive | **Smaller** — fewer directs = fewer transitives |
| Binary extensions | Some | Same (can't replace these easily) |
| Python runtime | Same | Same |
| C libraries | Same | Same |
| Processor | Same | Same |

The total code running hasn't changed much. But the proportion you understand and control has shifted significantly upward. That's the agency gain.

## How This Connects to Issues FS

### Tracking agency

Issues FS can track the dependency graph as issue types — every dependency is a node, every transitive dependency is a connected node. When you replace a dependency with your own code, the graph shows the shift: dependency node removed, new code nodes added, agency increased. Measurable.

### Blast radius clarity

With fewer dependencies, the blast radius of any change is more contained and more visible. Your code graph (in Issues FS) covers a larger proportion of the actual running system. Fewer black boxes.

### The code quality feedback loop

Every piece of generated code that enters the repo goes through the quality culture checks (from the previous briefs): does it match the standard? Is it well-typed? Does the blast radius match the brief? The LLM wrote it, but you own it. It's YOUR code now, and it meets YOUR standards.

### Cost-benefit tracking

The cost control brief applies here too. Replacing a dependency isn't free — there's LLM cost, dev time, testing effort. But the benefit is reduced dependency risk, increased agency, smaller attack surface. Issues FS can track this trade-off per dependency replaced.

## For the Agents

- **Architect**: map the current dependency tree for our projects. Identify candidates for replacement — dependencies where we only use a fraction of the functionality and could feasibly write our own. Prioritise by: how much of the dependency do we use? How deep is its transitive tree? How stable is our alternative?
- **Dev**: when replacing a dependency, the generated code must meet the full quality bar. Type_Safe types, proper schemas, tested, documented. The point is NOT just removing the dependency — it's gaining agency over that functionality.
- **AppSec**: fewer dependencies = smaller supply chain attack surface. Track the reduction. Every dependency removed is a security win. Quantify it.
- **QA**: when we replace a dependency with our own code, the test coverage for that functionality needs to be as good or better than what the dependency provided. Define the testing requirements for dependency replacement.
- **Journalist**: this is a compelling narrative for the public website. "LLMs don't reduce your control over code — they increase it, if you do it right." Counter the prevailing fear narrative with evidence from our own practice.
