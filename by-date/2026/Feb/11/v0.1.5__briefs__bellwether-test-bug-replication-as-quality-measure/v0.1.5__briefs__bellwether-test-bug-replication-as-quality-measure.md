# The Bellwether Test: Can You Replicate a Bug in Code?

**version** v0.1.5  
**date** 11 Feb 2026  

## The Measure

Here's a simple bellwether for whether your codebase, your test infrastructure, and your team's understanding are at a good level: **when a bug is found, how quickly can you replicate it as a test?**

Not fix it. Replicate it. Write a test that reproduces the exact behaviour — the browser navigation, the error message, the weird behaviour, the feature that didn't work as expected. If you can do that quickly and easily, it tells you two things:

1. **You have good test infrastructure** — you can spin up the right state, access the right moment, invoke the right paths. The plumbing works.
2. **You have good understanding of the codebase** — you know where the bug is happening, you can navigate the layers, you can reason about what's going on. No opacity.

If you CAN'T do it quickly, that's a signal. Either the test infrastructure is inadequate, or the people involved don't understand the code well enough to replicate the behaviour. Both are problems worth knowing about.

## The Bug-Walking Pattern

When I find a bug, I "walk" it:

1. **Start with what was observed** — the browser navigation, the error message, the unexpected behaviour. Something happened. There's always an event.
2. **Write the first test** — as close as possible to what was recorded. This is the surface-level replication.
3. **Go deeper, layer by layer** — each new test goes one level deeper into the code. Replicate at the API level. Then at the service level. Then at the function level.
4. **Eventually find the root cause** — you keep narrowing until you find the exact place where the behaviour diverges from what's expected.

At every layer, you're writing tests. By the time you find the bug, you have a trail of tests that document the path from symptom to cause. Those tests stay in the codebase — they're regression protection forever.

## Technical Managers Should Write Tests, Not Screenshots

This is a specific point about how technical managers and senior engineers should communicate.

The typical pattern when a manager finds a bug: send a screenshot to the team, write a description in a ticket, say "hey, here's a bug." The team then has to figure out what happened, how to replicate it, where to look.

The better pattern: the technical manager writes a test. Or uses an LLM to write a test. The test replicates the bug — "here's the behaviour I'm seeing." And optionally: "here's what I'd like to happen instead" — a second test that shows the desired behaviour.

This is communicating in code. It's:

- **Precise** — no ambiguity about what was observed
- **Executable** — the team can run it and see the bug immediately
- **Verifiable** — when the bug is fixed, the test passes
- **Documented** — the test stays as a permanent record of what went wrong and what "fixed" means

If the technical manager can't write this test (or get an LLM to write it), that itself is a signal — either the codebase is too opaque, the test infrastructure is too weak, or the manager doesn't understand the code well enough.

## The Bellwether Metric

You could actually measure this:

- **Time to first replication test** — from "bug observed" to "test that reproduces it exists." Minutes? Hours? Days? Never?
- **Depth of replication** — did we only replicate at the surface (browser test) or did we walk it all the way to the root cause?
- **Who can do it** — can only the original developer replicate bugs? Can any team member? Can the technical manager? The wider the pool, the healthier the codebase.

A team where anyone can replicate any bug as a test within minutes has a fundamentally different quality posture than a team where bugs sit in Jira with a screenshot and a prayer.

## What This Requires

For this to work, the codebase needs:

- **Easy state setup** — spin up the right conditions for any test without boilerplate hell
- **Layer accessibility** — you can test at any level (UI, API, service, function) without fighting the architecture
- **No opacity** — you can see what's happening, trace the flow, understand the path
- **Good primitives** — Type_Safe schemas, domain types, runtime validation — so data is well-formed and state is predictable
- **Fast feedback** — tests run quickly, results are clear, the loop is tight

These are all properties of well-architected code. The bellwether test works because it measures all of them at once.

## How Issues FS Enables This

Although this memo was recorded before we started working on Issues FS, a well-populated Issues FS graph would make this workflow dramatically more effective.

### Bug-to-test traceability

When a bug is found, it becomes an issue in Issues FS. The test that replicates it links to the issue. The fix that resolves it links to both. The entire trail — observation → replication test → root cause investigation → fix → regression test — is a connected graph. You can trace from any point to any other point.

### The sidecar connection

The sidecar artefacts (from the earlier brief) give you the code graph — functions, call paths, business meaning. When you're walking a bug, the sidecar tells you: this function is called by these paths, it's part of this workflow, these are the connected components. The bug-walking process is guided by the graph instead of done by memory and intuition.

### Bellwether as a dashboard metric

The "time to first replication test" metric can be tracked as an issue property. Over time, the Issues FS graph shows you: is replication getting faster or slower? For which areas of the codebase is it easy vs hard? Where are the opacity spots? The bellwether becomes a measurable, trackable, graphable indicator.

### Technical manager workflow

The manager finds a bug. They create an issue in Issues FS with the observation. They (or an LLM) write the replication test and link it to the issue. The developer picks up the issue, already has the test, walks it deeper, links each deeper test to the same issue. The fix gets its own branch (atomic branch workflow), links to the issue, the test passes, the branch merges. The entire flow is one connected graph, from "I saw something weird" to "it's fixed and tested."

### The blast radius connection

The bug-walking pattern is the inverse of the blast radius analysis from the earlier briefs. Blast radius asks: "if I change this, what breaks?" Bug-walking asks: "this broke, what caused it?" Both are graph traversals on the same code/issue graph. Same infrastructure, opposite direction.

## For the Agents

- **Architect**: define what "easy state setup" means for our codebase. Can any test spin up the right conditions without external dependencies? If not, what's missing?
- **QA**: the bellwether metric is yours to track. Start measuring: how long does it take to go from "bug observed" to "test that reproduces it"? Track per area of codebase. Report trends.
- **Dev**: every bug fix should follow the bug-walking pattern. Don't jump to fixing — write the replication test first, walk it deeper, THEN fix. The tests are as valuable as the fix.
- **Conductor**: when a bug is reported, ensure the issue links to the replication test before any fix work starts. The test IS the acceptance criteria — "fixed" means "this test passes."
- **Journalist**: "can your CTO replicate a bug in code?" is a provocative article angle. The bellwether concept is accessible and immediately resonant with technical audiences.
