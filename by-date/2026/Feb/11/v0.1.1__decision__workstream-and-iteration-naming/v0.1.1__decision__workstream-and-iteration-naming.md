# Naming Decision: Workstream + Iteration

**version** v0.1.4  
**date** 10 Feb 2026  
**decision** adopted  

## Decision

We are using **Workstream** and **Iteration** as our terms for grouping and scheduling work in this project. These replace the conventional "Epic" and "Sprint" terminology.

- **Workstream** — a container of related work towards a specific goal (e.g. "MVP Release Infrastructure")
- **Iteration** — a time-bound cycle of work within a workstream

These should be added as first-class node types in Issues FS (alongside the existing types like Story, Task, Spike, etc.).

## Why Not Epic and Sprint

**Epic** is Jira terminology that has leaked into general usage. It doesn't describe what it actually is — it's just a group of related work. Calling it an "epic" adds mythology where none is needed. A workstream says exactly what it is: a stream of work flowing in a direction.

**Sprint** implies fixed timeboxes and carries heavy Scrum methodology baggage. It also implies urgency and speed as a default, which creates the wrong incentive. Our work is driven by "what does done look like" not by a calendar date. Iteration is honest about what's actually happening: we're iterating. We do a cycle, we review, we go again.

## Alternatives Considered

### For grouping work (replacing Epic)

| Name | Why considered | Why not chosen |
|------|---------------|----------------|
| **Workstream** | Clear, no baggage, says what it is | ✅ **Chosen** |
| Brief | Already used naturally for the document that kicks off work | Conflates the "container of work" with the "document describing it" |
| Track | Short and clean | A bit too generic, could mean anything |
| Batch | Honest about what it is | Feels transactional, lacks direction |
| Phase | Already used in the roadmap (Phase 1, 2, etc.) | Better suited for the macro-level roadmap, not individual work groups |
| Initiative | Widely understood | A bit corporate/formal for our style |
| Wave | Works well with "workstream" metaphor | Slightly abstract |

### For time-bound cycles (replacing Sprint)

| Name | Why considered | Why not chosen |
|------|---------------|----------------|
| **Iteration** | Honest, no baggage, self-explanatory | ✅ **Chosen** |
| Cycle | Neutral, implies iteration | Slightly mechanical |
| Push | Action-oriented, matches natural speech ("the current push") | Implies urgency, similar problem to Sprint |
| Drop | From product/release culture, works with versioning | More about the output than the process |
| Round | Simple, no baggage | A bit informal, lacks direction |
| Milestone | Outcome-focused rather than time-focused | More of a marker than a container of work |

## How These Work Together

A **Workstream** contains one or more **Iterations**. An Iteration contains Stories, Tasks, Spikes, Tests, etc.

```
Workstream: MVP Release Infrastructure
├── Iteration: v0.1.4
│   ├── Story: Lambda deployment pipeline
│   ├── Story: Docker build + deploy
│   ├── Task: Playwright E2E test scaffolding
│   └── Spike: LocalStack S3 integration test setup
├── Iteration: v0.1.5
│   ├── Story: Fargate deployment
│   ├── Story: EC2 / AMI deployment
│   └── Story: GCP Cloud Run deployment
```

## For All Agents

Use these terms in all docs, issues, and communication going forward. Update any existing references to "Epic" or "Sprint" when you encounter them.
