## Executive Summary

This document defines `Issues-FS__Lexicon` — a foundational repository that provides the common language for the entire Issues-FS ecosystem. It contains ontologies, taxonomies, shared schemas, domain definitions, base classes, and coordination protocols that every other repo depends on. Together with `osbot-utils`, it forms one of two universal dependencies: osbot-utils defines **how we write code**; Lexicon defines **what we talk about**.

The package name is `issues-fs-lexicon`, published to PyPI, and required by every Issues-FS repository.

---

## Why: The Common Language Problem

### Every Ecosystem Develops a Vocabulary

As the Issues-FS ecosystem grows — core library, service layer, clients, integrations, role repos — each component inevitably develops its own understanding of shared concepts. What is a "status"? What statuses are valid? What does "resolved" mean versus "completed" versus "closed"? What link types exist between issues? What fields does a Decision have? What roles exist?

Without a single source of truth, these definitions drift. The core library has one understanding of issue types, the service has a slightly different one, the GitHub integration maps to a third interpretation, and the QA role repo defines its own statuses for defects. This drift is invisible at first and painful later — manifesting as subtle bugs, schema mismatches, broken integrations, and agents talking past each other.

### The Two-Dependency Invariant

The architectural insight is that every Issues-FS repository, without exception, should depend on exactly two foundational packages:

```
Every Issues-FS repo
    ├── osbot-utils          → Structural patterns (Type_Safe, how we build)
    └── issues-fs-lexicon    → Domain semantics (vocabulary, what we mean)
```

This invariant means:

- **Any repo can reference any shared concept** without importing heavyweight dependencies. A role repo doesn't need to depend on `issues-fs` (the core library) just to reference an issue type definition. It depends on `issues-fs-lexicon`.
- **Vocabulary changes propagate cleanly.** When a new issue type is added or a status transition is modified, it's changed in one place. Every consumer picks it up on their next version bump.
- **New repos start with a shared vocabulary immediately.** There's no bootstrapping problem — the common language is available from the first line of code.

### Why Not Just Schemas?

A `__Schemas` repo would be too narrow. The common language includes:

| Artifact Type | Example | Why It's Not Just a Schema |
|--------------|---------|---------------------------|
| **Ontology** | "A Decision is a type of Issue. A Handoff links two Roles." | Defines what concepts exist and how they relate |
| **Taxonomy** | issue-types.json, link-types.json, role-types.json | Classifies concepts into hierarchies |
| **Schema** | Decision issue fields, Handoff issue fields | Defines the structure of a specific concept |
| **State Machine** | Valid status transitions per issue type | Defines behavioral rules |
| **Vocabulary** | Status definitions, priority definitions, severity levels | Defines the meaning of terms |
| **Base Classes** | Type_Safe base classes for domain objects | Shared code that encodes the vocabulary |
| **Constants** | Standard field names, default values, enum definitions | Prevents string-literal drift |
| **Documentation** | Canonical definitions of every domain term | Human-readable reference |

A lexicon encompasses all of these. It is the complete vocabulary of the Issues-FS domain — the terms, their definitions, their relationships, their structures, and their behavioral rules.

### The Consistency Tests

The `test__consistency/` directory deserves special attention. These tests validate that the Lexicon is internally coherent:

- Every issue type defined in the taxonomy has a corresponding schema
- Every schema has a corresponding state machine definition
- Every status referenced in a state machine exists in the status taxonomy
- Every role referenced in coordination schemas exists in the role taxonomy
- Every link type used in schemas exists in the link type taxonomy
- The MGraph representations are in sync with the Python definitions

These tests are the Librarian role's best friend. They catch vocabulary drift before it reaches any consumer.

## How: Integration Patterns

### Consumer Usage

Every Issues-FS repo imports from the Lexicon. Here's how each layer uses it:

#### Core Library (Issues-FS)

```python
from issues_fs_lexicon.schemas.schemas__core    import Schema__Task
from issues_fs_lexicon.taxonomies               import taxonomy__issue_types
from issues_fs_lexicon.state_machines           import transitions__task
from issues_fs_lexicon.base_classes             import Base__Issue
from issues_fs_lexicon.constants.enums          import Enum__Status

class Node__Task(Base__Issue):
    """A task node in the issue graph."""

    def validate_transition(self, new_status: Enum__Status):
        return transitions__task.is_valid(self.status, new_status)
```

#### Service Layer (Issues-FS__Service)

```python
from issues_fs_lexicon.schemas.schemas__core         import Schema__Task
from issues_fs_lexicon.schemas.schemas__coordination  import Schema__Decision
from issues_fs_lexicon.taxonomies                     import taxonomy__issue_types
from issues_fs_lexicon.constants                      import const__field_names

# API endpoint uses Lexicon schemas for request/response validation
@router.post("/api/nodes/task")
def create_task(task: Schema__Task):
    # Schema validation is handled by the Lexicon type
    ...
```

#### Role Repos (Issues-FS__Dev__Role__QA)

```python
from issues_fs_lexicon.schemas.schemas__coordination  import Schema__Defect
from issues_fs_lexicon.schemas.schemas__coordination  import Schema__Approval
from issues_fs_lexicon.state_machines                 import transitions__defect
from issues_fs_lexicon.constants.enums                import Enum__Severity

# QA role creates defects using the shared schema
defect = Schema__Defect(
    title       = "API returns 500 on empty payload",
    severity    = Enum__Severity.P1,
    found_in    = "Issues-FS__Service",
    steps       = ["Send POST to /api/nodes/task with empty body",
                    "Observe 500 instead of 400"                  ],
)
```

#### Integration Services (Issues-FS__Service__GitHub)

```python
from issues_fs_lexicon.taxonomies    import taxonomy__issue_types
from issues_fs_lexicon.taxonomies    import taxonomy__statuses
from issues_fs_lexicon.ontologies    import ontology__links

# Map GitHub issue labels to Issues-FS taxonomy
def map_github_label_to_issue_type(label: str) -> str:
    """Maps a GitHub label to the canonical Issues-FS issue type."""
    mapping = {
        "bug"         : taxonomy__issue_types.BUG,
        "enhancement" : taxonomy__issue_types.FEATURE,
        "question"    : taxonomy__issue_types.TASK,
    }
    return mapping.get(label, taxonomy__issue_types.TASK)
```

### Relationship to Existing Packages

The Lexicon changes the dependency graph. Currently, `Issues-FS__Service__Client__Python` holds schemas that both the core library and the service depend on. With the Lexicon, the responsibility splits:

| Concern | Before (Client__Python) | After (split) |
|---------|------------------------|----------------|
| Domain schemas (what an issue looks like) | Client__Python | **Lexicon** |
| API schemas (request/response shapes) | Client__Python | Client__Python (remains) |
| Python API client | Client__Python | Client__Python (remains) |
| Issue type definitions | Issues-FS core (json files) | **Lexicon** (migrated) |
| Link type definitions | Issues-FS core (json files) | **Lexicon** (migrated) |
| Status definitions | Scattered / implicit | **Lexicon** (new) |
| State machine rules | Implicit in code | **Lexicon** (new, explicit) |

The key distinction: **Lexicon owns domain semantics** (what a Task is, what statuses it can have). **Client__Python owns API mechanics** (how to call the REST endpoint to create a Task). Client__Python itself depends on Lexicon for the domain types.

## What Lives Where: Decision Guide

When adding something new to the ecosystem, this guide determines whether it belongs in the Lexicon or elsewhere:

| Question | If Yes → | If No → |
|----------|----------|---------|
| Is it a concept that multiple repos need to agree on? | **Lexicon** | Repo-specific |
| Is it an issue type, link type, status, or priority? | **Lexicon** | — |
| Is it a schema for a domain object (not an API request)? | **Lexicon** | — |
| Is it a state machine or transition rule? | **Lexicon** | — |
| Is it a base class that domain objects extend? | **Lexicon** | — |
| Is it an API request/response schema? | Client__Python | — |
| Is it an API client method? | Client__Python | — |
| Is it a ROLE.md template or prompt template? | Role repo or Role__Shared | — |
| Is it implementation code (graph operations, storage)? | Issues-FS core | — |
| Is it a test specific to one component? | That component's repo | — |
| Is it a cross-cutting consistency validation? | **Lexicon** (test__consistency) | — |

### The Litmus Test

When in doubt, ask: **"If this definition were wrong or missing, how many repos would break?"**

- If the answer is "just this one" → it belongs in this repo.
- If the answer is "two or more" → it belongs in the Lexicon.
- If the answer is "all of them" → it definitely belongs in the Lexicon.

## Migration Path

Adopting the Lexicon doesn't require a big-bang migration. It can be introduced incrementally:

### Phase 1: Foundation

1. Create `Issues-FS__Lexicon` repo with base structure
2. Add `osbot-utils` as the only dependency
3. Migrate `issue-types.json` and `link-types.json` from Issues-FS core
4. Create Python enums and constants for existing types
5. Publish `issues-fs-lexicon` v0.1 to PyPI

### Phase 2: Core Integration

1. Add `issues-fs-lexicon` as dependency to Issues-FS core
2. Replace inline type references with Lexicon imports
3. Add `issues-fs-lexicon` as dependency to Issues-FS__Service
4. Update Client__Python to depend on Lexicon for domain schemas
5. Write consistency tests

### Phase 3: Coordination Layer

1. Add coordination issue type schemas (Decision, Handoff, Defect, etc.)
2. Add state machine definitions for all issue types
3. Add role taxonomy and role base classes
4. Role repos adopt Lexicon dependency
5. Publish `issues-fs-lexicon` v0.2

### Phase 4: Semantic Graphs

1. Add MGraph-native representations of ontologies and taxonomies
2. Build graph-based queries: "show me all issue types that can transition to 'closed'"
3. Enable ontology-driven UI rendering (issue forms generated from Lexicon schemas)
4. Publish `issues-fs-lexicon` v1.0

## The Ontology-Taxonomy-Schema Stack

The Lexicon introduces a layered semantic model. Understanding the layers is essential:

```
┌─────────────────────────────────────────────────────────┐
│                      ONTOLOGY                           │
│  "What concepts exist and how do they relate?"          │
│                                                         │
│  An Issue HAS a Status. A Handoff LINKS two Roles.      │
│  A Decision SUPERSEDES another Decision.                │
│  A Defect IS-A type of Issue.                           │
└──────────────────────────┬──────────────────────────────┘
                           │ concepts classified into
┌──────────────────────────▼──────────────────────────────┐
│                      TAXONOMY                           │
│  "How are concepts organized into categories?"          │
│                                                         │
│  Issue Types: Task, Bug, Epic, Feature, Decision,       │
│               Handoff, Defect, Release ...              │
│  Statuses:    open, in_progress, completed, blocked ... │
│  Priorities:  P0, P1, P2, P3                            │
│  Roles:       Dev, QA, Architect, Conductor ...         │
└──────────────────────────┬──────────────────────────────┘
                           │ categories structured as
┌──────────────────────────▼──────────────────────────────┐
│                       SCHEMA                            │
│  "What fields does a specific concept have?"            │
│                                                         │
│  Decision: title, context, options, recommendation,     │
│            impact, decided_by, decided_on, supersedes   │
│  Defect:   title, severity, steps, expected, actual,    │
│            found_in, linked_to                          │
└──────────────────────────┬──────────────────────────────┘
                           │ instances governed by
┌──────────────────────────▼──────────────────────────────┐
│                   STATE MACHINE                         │
│  "What transitions are valid for this concept?"         │
│                                                         │
│  Decision: proposed → under_review → accepted           │
│  Defect:   open → investigating → fixed → verified     │
│  Handoff:  pending → in_progress → completed            │
└─────────────────────────────────────────────────────────┘
```

Each layer depends on the one above it:

- You can't define a taxonomy without an ontology (what are you classifying?)
- You can't define a schema without a taxonomy (what category does this schema belong to?)
- You can't define a state machine without a schema (what status field are you transitioning?)

The Lexicon repo owns all four layers. This is what makes it more than a schemas repo — it's the full semantic stack.

## Future: The Lexicon as a Graph

As the ecosystem matures, the Lexicon's artifacts should themselves become MGraph graphs. This means:

- The ontology is a graph of concepts and relationships, queryable via MGraph-DB
- The taxonomy is a tree within that graph, navigable programmatically
- Schemas are graph nodes with typed edges to their fields
- State machines are subgraphs of status nodes connected by transition edges

This enables powerful capabilities:

- **"Show me all issue types that a QA role can create"** → graph query joining role taxonomy to issue type taxonomy via coordination ontology
- **"What fields does a Decision share with a Handoff?"** → graph query comparing schema nodes
- **"Can a Defect transition from 'open' to 'verified' directly?"** → graph path query on state machine subgraph
- **"Which issue types have no state machine defined?"** → consistency query (replaces test__consistency)

The Lexicon starts as Python classes and JSON files. It evolves into a live semantic graph that the entire ecosystem queries at runtime. The data files are the seed; the graph is the mature form.

## Decisions Log

| # | Decision | Rationale |
|---|----------|-----------|
| L1 | Name is **Lexicon**, not Schemas, Ontology, Commons, or KB | Lexicon encompasses the full scope: ontologies, taxonomies, schemas, state machines, base classes, constants, and documentation. It signals "complete vocabulary" not just "data structures." |
| L2 | **Universal dependency** alongside osbot-utils | Every repo needs the shared vocabulary. Making it universal prevents the "which package do I import this from?" problem and ensures vocabulary consistency. |
| L3 | **Domain schemas live in Lexicon; API schemas stay in Client__Python** | Clean separation: Lexicon defines what a Decision *is*; Client__Python defines how to send a Decision to the API. Different concerns, different change rates. |
| L4 | **JSON data files migrated from Issues-FS core** | issue-types.json and link-types.json are vocabulary, not implementation. They belong in the vocabulary repo. |
| L5 | **Consistency tests live in the Lexicon** | The Lexicon is the only place that has visibility across all domain definitions. Cross-cutting consistency validation belongs where all the definitions are. |
| L6 | **Incremental migration, not big-bang** | The Lexicon can be introduced alongside existing patterns and absorb definitions gradually. No repo needs to change until it's ready. |
| L7 | **Evolve toward MGraph-native representations** | Start with Python + JSON for simplicity. Add graph representations when the ecosystem is mature enough to benefit from graph queries over the vocabulary itself. |
