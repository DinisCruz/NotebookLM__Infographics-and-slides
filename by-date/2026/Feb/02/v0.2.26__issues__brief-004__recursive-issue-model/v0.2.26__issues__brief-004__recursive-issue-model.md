## Executive Summary

This document synthesizes all previous briefs into a unified architecture and establishes the **core principles** of the graph-based issue tracking system.

### The Core Insight

> **Everything is an issue. An issue contains issues.**

This creates a **recursive, fractal structure** where:
- The atomic unit is an **issue** (not "node" — see naming decision below)
- An issue can contain child issues in an `issues/` folder
- Each level can define its own schema (issue types, link types)
- Any issue can be the entry point (the "root" for a given context)
- The filesystem structure **IS** the graph structure

## The Naming Decision: "Issue", Not "Node"

### Why We're Using "Issue"

The term "node" was a legacy artifact from early development. After careful consideration, **"issue"** is the correct name for our atomic unit:

| Reason | Explanation |
|--------|-------------|
| **Domain Language** | This is an issue tracking system — "issue" is the natural term |
| **Avoids Collision** | MGraph-DB uses "node" for graph primitives; we need separation |
| **Self-Describing** | `issue.json` immediately communicates purpose |
| **Consistent** | We already call them "issues" in conversation and docs |
| **No Conflict** | We don't have an "issue" issue type (that would be like having a "thing" type) |

### The Clean Namespace

```python
# CLEAR SEPARATION
Schema__Issue                   # Our domain object (the atomic unit)
Schema__Issue__Link             # A link between issues
Schema__MGraph__Node            # MGraph's graph primitive (for indexing)
Issue__Service                  # Service for issue operations

# vs. the OLD confusing namespace
Schema__Node                    # Our issue? Or a graph node? Unclear.
Schema__MGraph__Node            # MGraph's node — collision!
```

### File Naming

| Old | New | Purpose |
|-----|-----|---------|
| `node.json` | `issue.json` | The issue data file |
| `{type}/` folders | `issues/` folder | Child issues container |
| `*.mgraph.json` | `indexes/*.mgraph.json` | MGraph index files |

│   │   │   ├── issue.json                                                        │
│   │   │   └── issues/                   ◄── (recursive)                         │
│   │   └── {Child-2}/                                                            │
│   │       └── issue.json                                                        │
│   │                                                                              │
│   ├── config/                           ◄── OPTIONAL: Local schema              │
│   │   ├── issue-types.json                                                      │
│   │   └── link-types.json                                                       │
│   │                                                                              │
│   ├── indexes/                          ◄── OPTIONAL: MGraph indexes            │
│   │   └── issues.mgraph.json                                                    │
│   │                                                                              │
│   └── content/                          ◄── OPTIONAL: Attachments, files        │
│       └── ...                                                                   │
│                                                                                  │

### Top-Level Folders Have Semantic Meaning

| Folder | Purpose | When Present |
|--------|---------|--------------|
| `issue.json` | The issue itself | Always (required) |
| `issues/` | Child issues | When issue has children |
| `config/` | Local schema (types, links) | When overriding/extending parent schema |
| `indexes/` | MGraph index files | When subtree is indexed |
| `content/` | Attachments, documents | When issue has associated files |
| `history/` | Audit trail | Future: change history |

## The Unified `issues/` Folder

### Why One Folder, Not Type-Segregated Folders

**Old approach (type-segregated):**
```
Feature-42/
├── node.json
├── task/
│   ├── Task-1/node.json
│   └── Task-2/node.json
├── bug/
│   └── Bug-1/node.json
└── user-story/
    └── UserStory-1/node.json
```

**New approach (unified):**
```
Feature-42/
├── issue.json
└── issues/
    ├── Bug-1/issue.json
    ├── Task-1/issue.json
    ├── Task-2/issue.json
    ├── UserStory-1/issue.json
    ├── UserStory-2/issue.json
    └── UserStory-3/issue.json
```

### The Type is Encoded, Not Folder-Segregated

The issue type is encoded in:
1. **The label** — `Task-1`, `Bug-1`, `UserStory-1` (self-describing)
2. **The `issue.json`** → `issue_type` field
3. **NOT** in redundant parent folder structure

### Alphabetical Sorting = Natural Type Grouping

```
Feature-42/issues/
├── Bug-1/           ┐
├── Bug-2/           ┘ Bugs grouped together
├── Task-1/          ┐
├── Task-2/          │ Tasks grouped together
├── Task-3/          ┘
├── UserStory-1/     ┐
├── UserStory-2/     │ Stories grouped together
└── UserStory-3/     ┘
```

**The naming convention IS the grouping.** Works everywhere:
- Filesystem (`ls`)
- GitHub file browser
- `git status`
- IDE file trees
- `tree` command

## Core Principle: The Rule of 7±2

### Direct Children as Health Indicator

> **Rule of 7±2:** An issue's `issues/` folder should ideally contain **fewer than 10 direct children**. More than that suggests the need to nest issues deeper into a proper hierarchy.

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                         THE RULE OF 7±2                                          │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   HEALTHY (5 direct children):                                                  │
│   Feature-42/issues/                                                            │
│   ├── UserStory-1/      ◄── Contains its own tasks/bugs                        │
│   ├── UserStory-2/      ◄── Contains its own tasks/bugs                        │
│   ├── UserStory-3/      ◄── Contains its own tasks/bugs                        │
│   ├── Bug-1/            ◄── Feature-level bug (not story-specific)             │
│   └── Task-1/           ◄── Feature-level task (setup, etc.)                   │
│                                                                                  │
│   ✓ Clear structure                                                             │
│   ✓ Easy to navigate                                                            │
│   ✓ Each story contains its own work                                           │
│                                                                                  │
│   ═══════════════════════════════════════════════════════════════════════════   │
│                                                                                  │
│   UNHEALTHY (50 direct children):                                               │
│   Feature-42/issues/                                                            │
│   ├── Bug-1/                                                                    │
│   ├── Bug-2/                                                                    │
│   ├── Bug-3/                                                                    │
│   ├── ... (15 more bugs)                                                        │
│   ├── Task-1/                                                                   │
│   ├── Task-2/                                                                   │
│   ├── ... (25 more tasks)                                                       │
│   └── UserStory-1/  (lonely, not containing its tasks)                         │
│                                                                                  │
│   ✗ Flat mess                                                                   │
│   ✗ Hard to navigate                                                            │
│   ✗ No logical grouping                                                         │
│   ✗ NEEDS REFACTORING — move tasks/bugs into their parent stories              │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### The Metric

| Direct Children | Health | Action |
|-----------------|--------|--------|
| 1-5 | ✅ Excellent | Well-structured |
| 6-9 | ✅ Good | Acceptable, monitor growth |
| 10-15 | ⚠️ Warning | Consider restructuring |
| 15+ | ❌ Unhealthy | Needs refactoring |
| 50+ | 🚨 Critical | Architectural problem |

### The Evolution Path

1. **Start flat** — Just throw issues in `issues/`
2. **Notice growth** — Too many items? Rule of 7±2 triggered
3. **Refactor down** — Move tasks/bugs into their parent stories
4. **Add indexes** — When subtree is large enough to benefit
5. **Repeat** — Same pattern applies at every level

**No upfront design required. The structure evolves with understanding.**

The filesystem naturally enforces good architecture:

├─────────────────────────────────────────────────────────────────────────────────┤

│   ────────────────────────────────────────────────────────────────────────────  │
│                                                                                  │

│                                                                                  │

│                                                                                  │
│   Can't duplicate folder names     →    Forces unique labels per container     │

## The Two Identifiers: `issue_id` vs `label`

### Why Both Exist

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    issue_id vs label                                             │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   issue_id (Obj_Id / GUID)                                                      │
│   ────────────────────────                                                      │
│   • Globally unique across entire system                                        │
│   • Random, generated once, NEVER changes                                      │
│   • Used for ALL links between issues                                          │
│   • Example: "a1b2c3d4", "f9e8d7c6"                                            │
│   • CANNOT conflict (by design)                                                │
│                                                                                  │
│   label (Type-Index)                                                            │
│   ──────────────────                                                            │
│   • Human-readable identifier                                                   │
│   • Format: "{Type}-{Number}" (e.g., Task-17, Bug-5)                           │
│   • Unique within immediate parent `issues/` folder                            │
│   • CAN be duplicated across different parents (and that's OK!)                │
│   • The actual numbers don't matter — usability matters                        │
│                                                                                  │
│   KEY INSIGHT:                                                                  │
│   ─────────────                                                                 │
│   "It doesn't matter if Project-A has Task-17 and Project-B has Task-17.       │
│    Within THIS context, 'Task-17' is clear and unambiguous."                   │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Label Conflicts Are Expected (And Handled)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    LABEL CONFLICTS: A FEATURE                                    │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   SCENARIO: Two features both have Task-1                                       │
│                                                                                  │
│   Feature-11/issues/Task-1/    issue_id: "a1b2c3d4"                            │
│   Feature-12/issues/Task-1/    issue_id: "e5f6g7h8"   ◄── SAME label, OK!      │
│                                                                                  │
│   WHY THIS IS FINE:                                                             │
│   • issue_ids are different (links work correctly)                             │
│   • Labels are contextual (Task-1 OF Feature-11)                               │
│   • File paths are different (no filesystem conflict)                          │
│   • Each feature has its own numbering sequence                                │
│                                                                                  │
│   ─────────────────────────────────────────────────────────────────────────     │
│                                                                                  │
│   MOVING CREATES A CONFLICT — FILESYSTEM DETECTS IT:                           │
│                                                                                  │
│   $ mv Feature-12/issues/Task-1  Feature-11/issues/Task-1                      │
│   ERROR: Folder already exists!                                                 │
│                                                                                  │
│   THE FILESYSTEM IS OUR FRIEND:                                                 │
│   • Conflict detected IMMEDIATELY                                              │
│   • Can't accidentally overwrite                                               │
│   • Must resolve before proceeding                                             │
│                                                                                  │
│   RESOLUTION:                                                                   │
│   1. Rename to next available: Task-1 → Task-4                                 │
│   2. Update issue.json label field                                             │
│   3. Move succeeds                                                             │
│   4. issue_id unchanged, all links still work!                                 │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## Containers of Containers: The Recursive Model

### Every Issue Can Contain Issues

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    RECURSIVE NESTING                                             │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   Project-1/                            ◄── Level 0: Project                    │
│   ├── issue.json                                                                │
│   └── issues/                                                                   │
│       └── Version-1/                    ◄── Level 1: Version                    │
│           ├── issue.json                                                        │
│           └── issues/                                                           │
│               └── Feature-11/           ◄── Level 2: Feature                    │
│                   ├── issue.json                                                │
│                   └── issues/                                                   │
│                       └── UserStory-1/  ◄── Level 3: User Story                 │
│                           ├── issue.json                                        │
│                           └── issues/                                           │
│                               └── Task-1/ ◄── Level 4: Task                     │
│                                   ├── issue.json                                │
│                                   └── issues/                                   │
│                                       └── Subtask-1/ ◄── Level 5               │
│                                           └── issue.json                        │
│                                                                                  │
│   Each level is the same pattern: issue.json + optional issues/                 │
│   Infinitely nestable. Same structure at every level.                          │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

│                                                                                  │
│   Higher in tree = wider graph                                                  │
│   Deeper in tree = narrower, focused graph                                     │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘

## Schema Inheritance

### Each Layer Can Define Its Own Schema

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    SCHEMA INHERITANCE                                            │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   Project-1/                                                                    │
│   ├── issue.json                                                                │
│   ├── config/                           ◄── Project-level schema               │
│   │   ├── issue-types.json              # [version, feature, task, bug, ...]   │
│   │   └── link-types.json               # [has-feature, has-task, blocks, ...]  │
│   └── issues/                                                                   │
│       └── Version-1/                                                            │
│           ├── issue.json                                                        │
│           ├── config/                   ◄── Version can EXTEND schema          │
│           │   └── issue-types.json      # Adds: [hotfix, patch]                │
│           └── issues/                                                           │
│               └── Feature-11/                                                   │
│                   ├── issue.json                                                │
│                   └── (no config/)      ◄── Inherits from Version-1            │
│                                                                                  │
│   INHERITANCE RULES:                                                            │
│   • If config/ exists → Use local schema (can extend parent)                   │
│   • If config/ missing → Inherit from parent                                   │
│   • Root must define base schema                                               │
│                                                                                  │
│   COMPATIBILITY FLOWS DOWNWARD:                                                 │
│   • Parent validates children (are their types allowed?)                       │
│   • Children don't validate upward (they just exist)                           │
│   • Enables importing external issue trees without modification                │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## Two Modes of Operation

### Consume Mode vs Fix Mode

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    TWO MODES OF OPERATION                                        │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   MODE 1: CONSUME (Normal Operation)                                            │
│   ───────────────────────────────────                                           │
│   • Load the data as-is                                                         │
│   • If conflicts exist, show warnings but don't block                          │
│   • Let user work — don't be in the way                                        │
│   • Conflicts shown in UI but not enforced                                     │
│                                                                                  │
│   USE WHEN: Day-to-day work, viewing issues, making progress                   │
│                                                                                  │
│   ═══════════════════════════════════════════════════════════════════════════   │
│                                                                                  │
│   MODE 2: FIX (Maintenance/Curation)                                            │
│   ────────────────────────────────────                                          │
│   • Scan for all conflicts and inconsistencies                                 │
│   • Present UI for resolution                                                  │
│   • Validate against schema                                                    │
│   • Ensure integrity before proceeding                                         │
│                                                                                  │
│   USE WHEN: After merge, after import, periodic cleanup, before release        │
│                                                                                  │
│   ═══════════════════════════════════════════════════════════════════════════   │
│                                                                                  │
│   CONFLICT TYPES:                                                               │
│   • Label collision (two Task-1s after merge)                                  │
│   • Schema violation (link type not allowed)                                   │
│   • Orphan issues (no parent link)                                             │
│   • Broken links (target issue_id not found)                                   │
│   • Rule of 7±2 violation (too many direct children)                           │
│   • Stale index (mgraph.json out of sync)                                      │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## Summary: The Ten Core Principles

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    THE TEN CORE PRINCIPLES                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   1. EVERYTHING IS AN ISSUE                                                     │
│      The atomic unit is an "issue" (not "node").                               │
│      issue.json is the only required file.                                     │
│                                                                                  │
│   2. ISSUES CONTAIN ISSUES                                                      │
│      An issue can have child issues in an issues/ folder.                      │
│      Infinitely nestable. Same pattern at every level.                         │
│                                                                                  │
│   3. THE RULE OF 7±2                                                            │
│      An issues/ folder should have <10 direct children.                        │
│      More = refactor into deeper hierarchy.                                    │
│                                                                                  │
│   4. FILESYSTEM = GRAPH                                                         │
│      The folder structure IS the containment graph.                            │
│      `tree` command = instant visualization.                                   │
│                                                                                  │
│   5. ORGANIC GROWTH                                                             │
│      Start simple, evolve complexity.                                          │
│      No upfront design required.                                               │
│                                                                                  │
│   6. AGENT-FRIENDLY                                                             │
│      Folder path = complete, self-contained context.                           │
│      Point an agent to a folder, it has everything.                            │
│                                                                                  │
│   7. DUAL IDENTITY                                                              │
│      issue_id: Global, immutable, for linking.                                 │
│      label: Local, human-readable, can duplicate across parents.               │
│                                                                                  │
│   8. SCHEMA INHERITANCE                                                         │
│      Each level can define or inherit its schema.                              │
│      Compatibility flows downward only.                                        │
│                                                                                  │
│   9. ANY ISSUE = ROOT                                                           │
│      Any issue can be the entry point.                                         │
│      Higher = wider view. Deeper = focused view.                               │
│                                                                                  │
│  10. CONSUME VS FIX                                                             │
│      Normal mode: Work with conflicts, don't block.                            │
│      Fix mode: Resolve conflicts, ensure integrity.                            │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```
