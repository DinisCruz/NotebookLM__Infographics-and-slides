## Executive Summary

This document addresses three interconnected concerns:

1. **Schema Visualization** — How to visualize and curate the "meta-schema" (which issue types can link to which, with what verbs)
2. **Folder-as-Schema** — The folder structure mirrors the graph structure; each folder is a mini-database
3. **Label Uniqueness Rules** — Labels must be unique within a folder, but can be duplicated across parallel folders

These features enable better schema governance, movable work units (like releases), and scalable issue organization.

## Part 1: Schema Visualization

### The Problem

In complex systems (like JIRA at scale), you end up with:
- Many issue types (bug, task, feature, epic, story, subtask, incident, change request...)
- Many link types (blocks, depends-on, duplicates, relates-to, implements, tests...)
- **No clear understanding of which types can connect to which**

Eventually, you lose track of the valid relationships and the schema becomes unmaintainable.

## Part 2: Folder Structure Mirrors Graph Structure

### The Principle

> "Each folder fundamentally represents a type of node, like a mini-database, and should be self-contained."

The folder hierarchy should match the logical hierarchy of issues:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                FOLDER STRUCTURE = GRAPH STRUCTURE                                │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   LOGICAL GRAPH:                        FILE SYSTEM:                            │
│                                                                                  │
│   Version-1 (v0.1.5)                    .issues/data/version/Version-1/         │
│       │                                     ├── node.json                       │
│       ├── Feature-11 (Issue Editor)         └── feature/                        │
│       │       │                                  ├── Feature-11/                │
│       │       ├── Task-2 (Edit form)             │   ├── node.json              │
│       │       ├── Task-3 (Comments)              │   ├── task/                  │
│       │       └── Bug-1 (Validation)             │   │   ├── Task-2/node.json   │
│       │                                          │   │   └── Task-3/node.json   │
│       └── Feature-12 (Graph View)                │   └── bug/                   │
│               │                                  │       └── Bug-1/node.json    │
│               └── Task-6 (D3 component)          └── Feature-12/                │
│                                                      ├── node.json              │
│                                                      └── task/                  │
│                                                          └── Task-6/node.json   │
│                                                                                  │
│   The folder structure IS the containment graph.                                │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Movable Work Units

Because folders are self-contained, they become **movable work units**:

```

│                                                                                  │

│   ├── Version-1/  (v0.1.5 - RELEASED)                                          │
│   │   └── feature/...                                                          │
│   └── Version-2/  (v0.2.0 - IN PROGRESS)                                       │
│       └── feature/...                                                          │
│                                                                                  │
│   AFTER (archive released version):                                             │
│   .issues/data/version/                                                         │
│   └── Version-2/  (v0.2.0 - IN PROGRESS)                                       │
│       └── feature/...                                                          │
│                                                                                  │
│   .issues/archive/version/                                                      │
│   └── Version-1/  (v0.1.5 - RELEASED)   ◄── Entire folder moved               │

│                                                                                  │
│   ─────────────────────────────────────────────────────────────────────────     │
│                                                                                  │
│   USE CASE: Move feature to different version                                   │
│   ───────────────────────────────────────────                                   │

│   mv Version-1/feature/Feature-11  Version-2/feature/Feature-11                │

│                                                                                  │

│                                                                                  │
```

### The Fractal Nature

> "The schema should eventually be fractal — the atomic unit is an issue."

Every issue follows the same pattern:
- Has a `node_id` (globally unique)
- Has a `label` (Type-Index, e.g., `Bug-5`)
- Lives in a folder named by its label
- Can contain child issues in subfolders
- Can link to other issues via `node_id`

This is **self-similar at every level**:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                         FRACTAL ISSUE STRUCTURE                                  │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   LEVEL 0: The entire .issues/ folder                                           │
│            └── Contains: version/, feature/, task/, bug/, etc.                  │
│                                                                                  │
│   LEVEL 1: A version folder (Version-1/)                                        │
│            └── Contains: feature/, (and their children)                         │
│            └── Has: node.json, version.mgraph.json                              │
│                                                                                  │
│   LEVEL 2: A feature folder (Feature-11/)                                       │
│            └── Contains: task/, bug/, user-story/                               │
│            └── Has: node.json, feature.mgraph.json                              │
│                                                                                  │
│   LEVEL 3: A task folder (Task-2/)                                              │
│            └── Contains: (usually nothing, leaf node)                           │
│            └── Has: node.json                                                   │
│                                                                                  │
│   Each level has THE SAME STRUCTURE:                                            │
│   • node.json (the issue data)                                                  │
│   • Optional {type}.mgraph.json (index of subtree)                             │
│   • Child folders organized by type                                            │
│                                                                                  │
│   This is fractal — zoom in and you see the same pattern.                      │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## Part 3: Label Uniqueness Rules

### The Rule

> "Labels must be unique within a folder, but can be duplicated across parallel folders."

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                      LABEL UNIQUENESS RULES                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   RULE 1: Within a folder, labels MUST be unique                                │
│   ──────────────────────────────────────────────                                │
│                                                                                  │
│   Feature-11/task/                                                              │
│   ├── Task-1/   ✓                                                               │
│   ├── Task-2/   ✓                                                               │
│   ├── Task-3/   ✓                                                               │
│   └── Task-2/   ✗ INVALID! Duplicate within same folder                        │
│                                                                                  │
│   ─────────────────────────────────────────────────────────────────────────     │
│                                                                                  │
│   RULE 2: Across parallel folders, labels CAN be duplicated                     │
│   ──────────────────────────────────────────────────────────                    │
│                                                                                  │
│   Feature-11/task/                     Feature-12/task/                         │
│   ├── Task-1/   ✓                      ├── Task-1/   ✓  (SAME label, OK!)       │
│   ├── Task-2/   ✓                      ├── Task-2/   ✓  (SAME label, OK!)       │
│   └── Task-3/   ✓                      └── Task-3/   ✓  (SAME label, OK!)       │
│                                                                                  │
│   Each Feature has its OWN Task-1, Task-2, Task-3.                             │
│   They are DIFFERENT issues with DIFFERENT node_ids.                           │
│                                                                                  │
│   ─────────────────────────────────────────────────────────────────────────     │
│                                                                                  │
│   WHY THIS WORKS:                                                               │
│   ───────────────                                                               │
│                                                                                  │
│   • node_id is globally unique (the TRUE identifier)                           │
│   • label is locally unique (for human readability within context)             │
│   • Full path provides disambiguation:                                          │
│       Feature-11/task/Task-1  vs  Feature-12/task/Task-1                       │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Why Allow Duplicate Labels?

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    WHY ALLOW DUPLICATE LABELS?                                   │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   REASON 1: Natural Numbering                                                   │
│   ───────────────────────────                                                   │
│   Each feature naturally has "Task 1, 2, 3..."                                 │
│   Forcing global uniqueness leads to "Task-1, Task-47, Task-892..."            │
│   which is confusing and hard to work with.                                    │
│                                                                                  │
│   REASON 2: Self-Contained Units                                                │
│   ──────────────────────────────                                                │
│   A feature folder is self-contained.                                          │
│   When you're working on Feature-11, you only care about ITS tasks.            │
│   "Task-1" means "the first task of THIS feature."                             │
│                                                                                  │
│   REASON 3: Copy/Move Operations                                                │
│   ──────────────────────────────                                                │
│   When copying a feature as a template:                                        │
│   cp -r Feature-11 Feature-15                                                  │
│                                                                                  │
│   The task labels (Task-1, Task-2) can stay the same.                          │
│   Only node_ids need to be regenerated.                                        │
│                                                                                  │
│   REASON 4: Distributed/Federated Systems                                       │
│   ────────────────────────────────────────                                      │
│   Different teams/repos can have their own Task-1, Task-2, etc.               │
│   When merged, labels may collide — but node_ids won't.                        │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Parent Folder Maintains Index Consistency

Each parent folder is responsible for ensuring uniqueness among its direct children:

```python
class Schema__Folder__Index(Type_Safe):
    """Index maintained by each folder for its children."""
    folder_path   : Safe_Str__Path                               # e.g., "Version-1/Feature-11"
    node_id       : Obj_Id                                       # This folder's issue node_id
    child_types   : Dict__Child_Type_Indexes                     # Index per child type
    last_updated  : Timestamp_Now


class Schema__Child_Type_Index(Type_Safe):
    """Index for one child type within a folder."""
    child_type    : Safe_Str__Node_Type                          # e.g., "task"
    next_index    : Safe_UInt                                    # Next available: 4
    labels_used   : Set__Labels                                  # {"Task-1", "Task-2", "Task-3"}
    node_ids      : Dict__Label_To_NodeId                        # {"Task-1": "abc123", ...}
```

**Validation on create:**

```python
def create_issue_in_folder(folder_path: str, issue_type: str, title: str) -> Issue:
    # Load parent folder's index
    parent_index = load_folder_index(folder_path)
    
    # Get next available label for this type
    type_index = parent_index.child_types[issue_type]
    next_num = type_index.next_index
    label = f"{issue_type.title()}-{next_num}"
    
    # Verify uniqueness (belt and suspenders)
    while label in type_index.labels_used:
        next_num += 1
        label = f"{issue_type.title()}-{next_num}"
    
    # Create issue with globally unique node_id
    issue = Schema__Issue__Node(
        node_id = Obj_Id(),           # Globally unique
        label   = label,              # Locally unique within folder
        ...
    )
    
    # Update parent's index
    type_index.next_index = next_num + 1
    type_index.labels_used.add(label)
    type_index.node_ids[label] = issue.node_id
    save_folder_index(folder_path, parent_index)
    
    return issue
```

## Summary: The Three Levels of Identity

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    THREE LEVELS OF IDENTITY                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   LEVEL 1: node_id (Obj_Id)                                                     │
│   ─────────────────────────                                                     │
│   • Globally unique across entire system                                        │
│   • Never changes, even if issue moves                                         │
│   • Used for all links between issues                                          │
│   • Example: "a1b2c3d4"                                                        │
│                                                                                  │
│   LEVEL 2: label (Type-Index)                                                   │
│   ──────────────────────────                                                    │
│   • Unique within parent folder                                                │
│   • Can be duplicated across parallel folders                                  │
│   • Human-readable identifier                                                  │
│   • Example: "Task-1", "Bug-5", "Feature-11"                                   │
│                                                                                  │
│   LEVEL 3: path (Folder Path)                                                   │
│   ───────────────────────────                                                   │
│   • Full path from root to issue                                               │
│   • Always unique (filesystem enforced)                                        │
│   • Used for disambiguation in UI                                              │
│   • Example: "Version-1/Feature-11/task/Task-1"                                │
│                                                                                  │
│   LINKING USES: node_id (Level 1)                                              │
│   DISPLAY USES: label (Level 2) or path (Level 3) based on context             │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## Design Decisions

### 1. Schema Enforcement: Warn vs Reject

**Decision:** TBD — Likely warn on violation, don't hard reject

**Rationale:** Flexibility during development; strict enforcement can be enabled later

### 2. Label Reset on Move

**Decision:** Labels stay the same when moving folders

**Rationale:** 
- node_id is the true identity
- Labels are contextual convenience
- Changing labels would break human mental models

### 3. Index Storage Location

**Decision:** Each folder stores its own `_index.json` for children

**Rationale:** Self-contained folders; no central index bottleneck
