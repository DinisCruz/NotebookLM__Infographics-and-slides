## Executive Summary

This document proposes two interconnected enhancements to the issue tracking system:

1. **Hierarchical Folder Structure** — Issues organized in nested folders that mirror their logical relationships, where each folder is a self-contained mini-database
2. **No-Orphan Principle** — Every issue must be connected to at least one other issue, enabling complete graph traversal and visualization

These features work together: hierarchical folders create natural containment, while the no-orphan principle ensures everything remains connected for visualization and AI agent interaction.

## Part 1: Hierarchical Folder Structure

### The Current State (Flat Structure)

```
.issues/
├── issues.mgraph.json               # ROOT index
└── data/
    ├── bug/                         # All bugs at same level
    │   ├── Bug-1/node.json
    │   ├── Bug-2/node.json
    │   └── Bug-3/node.json
    ├── task/                        # All tasks at same level
    │   ├── Task-1/node.json
    │   ├── Task-2/node.json
    │   └── Task-3/node.json
    ├── feature/                     # All features at same level
    │   ├── Feature-1/node.json
    │   └── Feature-2/node.json
    └── version/
        └── Version-1/node.json
```

**Problem:** This flat structure doesn't reflect the natural hierarchy of issues. Version-1 contains Feature-1 which contains Task-1, but they're stored as siblings.

### The Proposed State (Hierarchical Structure)

```
.issues/
├── issues.mgraph.json               # GLOBAL index (all issues, all edges)
└── data/
    └── version/
        └── Version-1/               # Version folder = mini-database
            ├── node.json            # Version-1 issue data
            ├── version.mgraph.json  # Index for this subtree
            └── feature/
                ├── Feature-1/       # Feature folder = mini-database
                │   ├── node.json    # Feature-1 issue data
                │   ├── feature.mgraph.json
                │   ├── task/
                │   │   ├── Task-1/node.json
                │   │   └── Task-2/node.json
                │   ├── bug/
                │   │   └── Bug-1/node.json
                │   └── user-story/
                │       └── UserStory-1/node.json
                │
                └── Feature-2/
                    ├── node.json
                    ├── feature.mgraph.json
                    └── task/
                        └── Task-3/node.json
```

### The Key Insight

> "Each folder is a mini-database that can be moved around."

A folder containing an issue becomes a **self-contained unit** that includes:
- The issue's own data (`node.json`)
- Its MGraph index (`{type}.mgraph.json`)
- All child issues in nested folders
- All relationships within that subtree

### Benefits of Hierarchical Structure

| Benefit | Description |
|---------|-------------|
| **Locality** | Related issues are physically near each other |
| **Portability** | Move a feature folder = move all its tasks/bugs |
| **Natural Scoping** | `Feature-1/` contains everything about Feature-1 |
| **Simpler Indexes** | Each folder's MGraph only indexes its subtree |
| **Git-Friendly** | Branch a feature = branch all related issues |
| **AI-Friendly** | Agent can focus on one folder = focused context |

### Cross-Tree Links

Issues can still link across the hierarchy:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           CROSS-TREE LINKING                                     │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   Version-1/                                                                    │
│   ├── Feature-1/                                                                │
│   │   └── Bug-1/  ─────────── blocks ───────────┐                              │
│   │                                              │                              │
│   └── Feature-2/                                 │                              │
│       └── Task-3/ ◄──────────────────────────────┘                              │
│                                                                                  │
│   Bug-1 blocks Task-3, even though they're in different subtrees.               │
│   This edge exists in:                                                          │
│   • GLOBAL index (issues.mgraph.json) — for cross-tree queries                 │
│   • Bug-1's node.json links[] — source of truth                                │
│   • NOT in Feature-1's subtree index (unless we denormalize)                   │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Link Identity: node_id, NOT label

**Critical:** Links reference issues by `node_id` (Obj_Id), NOT by `label`.

### Updated Link Schema

```python
class Schema__Issue__Node__Link(Type_Safe):
    """Link from one issue to another."""
    link_type_id  : Obj_Id                                                       # Reference to link-types.json
    verb          : Safe_Str__Link_Verb                                          # has-task, blocks, depends-on
    target_id     : Obj_Id                                                       # UNIQUE issue identifier (NOT label!)
    target_label  : Safe_Str__Node_Label                                         # For display only, may become stale
    target_hash   : Safe_Str__Hash                                               # Hash of target's node.json content
    target_commit : Safe_Str__Git_Commit     = None                              # Git commit hash when link created
    created_at    : Timestamp_Now                                                # When link was created
    updated_at    : Timestamp_Now            = None                              # When link was last verified/updated


class Schema__Issue__MGraph__Edge__Data(Schema__MGraph__Edge__Data):
    """Edge data for MGraph representation of links."""
    link_type_id  : Obj_Id
    verb          : Safe_Str__Link_Verb
    target_hash   : Safe_Str__Hash                                               # For change detection
    target_commit : Safe_Str__Git_Commit     = None
    created_at    : Timestamp_Now
```

### When to Create Subtree Indexes

Not every folder needs its own MGraph index:

| Folder Type | Create Index? | Rationale |
|-------------|---------------|-----------|
| Version | Yes | Major organizational unit |
| Feature | Yes | Contains multiple children |
| User Story | Maybe | If it has many tasks |
| Task | Rarely | Usually a leaf node |
| Bug | Rarely | Usually a leaf node |

**Rule:** Create `{type}.mgraph.json` when a folder has 5+ descendants or will be queried independently.

## Part 2: No-Orphan Principle

### The Principle

> "There should never be an issue that does not have a link to something else."

Every issue in the system must be connected to at least one other issue. This creates a **fully connected graph** where:
- You can traverse from any issue to any other issue
- There are no "dangling" nodes
- The entire system is reachable from a single root

### Why This Matters

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                        WHY NO ORPHANS?                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   1. COMPLETENESS                                                               │
│      Every piece of work is accounted for in the system.                        │
│      Nothing falls through the cracks.                                          │
│                                                                                  │
│   2. TRACEABILITY                                                               │
│      Can trace any task back to its feature, version, and business goal.        │
│      "Why are we doing this?" is always answerable.                             │
│                                                                                  │
│   3. BLAST RADIUS VISUALIZATION                                                 │
│      Can see the impact of changes by traversing the graph.                     │
│      "What else is affected if this feature slips?"                             │
│                                                                                  │
│   4. AI/AGENT INTERACTION                                                       │
│      Agents can navigate the entire system via links.                           │
│      "Find all tasks related to authentication" just works.                     │
│                                                                                  │
│   5. CURATION & CLEANUP                                                         │
│      Orphans indicate stale data that should be deleted or connected.           │
│      The graph stays healthy and meaningful.                                    │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### Orphan Detection

An orphan is a node with **no incoming or outgoing links**:

```python
# Using MGraph-DB index
def find_orphans(mgraph: MGraph) -> List[Node_Id]:
    """Find nodes with no edges."""
    orphans = []
    
    for node_id in mgraph.data().nodes():
        incoming = mgraph.index().edges_index.edges_to_node(node_id)
        outgoing = mgraph.index().edges_index.edges_from_node(node_id)
        
        if not incoming and not outgoing:
            orphans.append(node_id)
    
    return orphans

# Or using MGraph__Index__Query
orphans = (mgraph.index()
                 .query()
                 .with_no_edges()
                 .collect())
```

class Schema__Graph__Health(Type_Safe):
    """Graph integrity metrics."""

## Design Decisions (Answered)

### 1. Hybrid Approach: Yes, Support Both

**Decision:** Support both flat and hierarchical folders during transition

**Rationale:** This enables the "meta" workflow — using this issue tracking system to manage its own development. The system works today with flat structure; hierarchical is an enhancement, not a replacement.

### 2. Bidirectional Links: Yes, Always Create Both Directions

**Decision:** When creating a link A → B, also create the inverse link B → A

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                        BIDIRECTIONAL LINKING                                     │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   When user links Feature-12 ──has-task──▶ Task-23:                            │
│                                                                                  │
│   Feature-12/node.json:                   Task-23/node.json:                    │
│   {                                       {                                      │
│     "links": [                              "links": [                           │
│       {                                       {                                  │
│         "verb": "has-task",                     "verb": "task-of",    ◄── INVERSE│
│         "target_id": "..Task-23..",             "target_id": "..Feature-12..",  │
│         "target_label": "Task-23"               "target_label": "Feature-12"    │
│       }                                       }                                  │
│     ]                                       ]                                    │
│   }                                       }                                      │
│                                                                                  │
│   BOTH files are updated when a link is created.                                │
│   This enables traversal in either direction.                                   │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Link Type Inverses (from link-types.json):**

| Verb | Inverse |
|------|---------|
| `has-task` | `task-of` |
| `has-feature` | `feature-of` |
| `has-bug` | `bug-of` |
| `blocks` | `blocked-by` |
| `depends-on` | `dependency-of` |

### ⛔ BANNED: Symmetric Links (e.g., `relates-to`)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│  ⛔⛔⛔                    SYMMETRIC LINKS ARE BANNED                    ⛔⛔⛔  │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   BANNED LINK TYPES:                                                            │
│   • relates-to                                                                  │
│   • associated-with                                                             │
│   • linked-to                                                                   │
│   • Any link where verb == inverse                                              │
│                                                                                  │
│   WHY? GRAPH EXPLOSION                                                          │
│   ─────────────────────                                                         │
│                                                                                  │
│   Symmetric links are the ROOT CAUSE of:                                        │
│   • "Graph explosion" — traversal explodes exponentially                       │
│   • "Big dot" visualization — everything connects to everything                │
│   • Unusable graphs at 2-3 degrees of separation                               │
│                                                                                  │
│   EXAMPLE OF THE PROBLEM:                                                       │
│   ───────────────────────                                                       │
│                                                                                  │
│   Task-1 ──relates-to──▶ Task-2                                                │
│   Task-2 ──relates-to──▶ Task-3                                                │
│   Task-3 ──relates-to──▶ Task-4                                                │
│   Task-4 ──relates-to──▶ Task-1   (cycle!)                                     │
│   Task-2 ──relates-to──▶ Task-5                                                │
│   Task-5 ──relates-to──▶ Task-6                                                │
│   ... (continues)                                                               │
│                                                                                  │
│   Query: "Show me Task-1's graph at depth=3"                                   │
│   Result: THE ENTIRE DATABASE (everything "relates" to everything)             │
│                                                                                  │
│           ┌─────┐                                                               │
│           │     │                                                               │
│       ┌───┴─────┴───┐                                                          │
│       │  THE BIG    │   ◄── This is what you get with symmetric links         │
│       │    DOT      │       Useless. Unnavigable. Unrenderable.               │
│       └───┬─────┬───┘                                                          │
│           │     │                                                               │
│           └─────┘                                                               │
│                                                                                  │
│   THE SOLUTION: DIRECTED PATHS                                                  │
│   ────────────────────────────                                                  │
│                                                                                  │
│   Instead of:  Task-1 ──relates-to──▶ Task-2                                   │
│                                                                                  │
│   Use:         Task-1 ──blocks──▶ Task-2        (Task-1 blocks Task-2)         │
│                Task-1 ──depends-on──▶ Task-2    (Task-1 needs Task-2 first)    │
│                Task-1 ──duplicates──▶ Task-2    (Task-1 is a dupe of Task-2)   │
│                Feature-1 ──has-task──▶ Task-1   (hierarchical containment)     │
│                                                                                  │
│   Directed links with distinct verbs enable:                                    │
│   • Clean graph traversal (follow the arrows)                                  │
│   • Meaningful visualization (hierarchy visible)                               │
│   • Efficient queries (navigate using direct paths)                            │
│                                                                                  │
│   ENFORCEMENT:                                                                  │
│   ─────────────                                                                 │
│   • link-types.json must NOT contain symmetric types                           │
│   • API validation: reject if verb == inverse                                  │
│   • Migration: convert existing "relates-to" to specific directed types        │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Allowed Link Types (all directed, verb ≠ inverse):**

| Verb | Inverse | Meaning |
|------|---------|---------|
| `has-task` | `task-of` | Containment: parent has child |
| `has-feature` | `feature-of` | Containment: version has feature |
| `has-bug` | `bug-of` | Containment: feature has bug |
| `has-story` | `story-of` | Containment: feature has user story |
| `blocks` | `blocked-by` | Dependency: A prevents B |
| `depends-on` | `dependency-of` | Dependency: A needs B first |
| `duplicates` | `duplicated-by` | A is a duplicate of B |
| `assigned-to` | `assignee-of` | A is assigned to person B |
| `implements` | `implemented-by` | A implements requirement B |
| `tests` | `tested-by` | A tests functionality B |

### 4. Index Granularity: Performance Optimization, Not Required

**Decision:** Indexes are optional performance optimization; can always be regenerated

**Key Insight:** If all indexes are deleted or issues are copied/restored without indexes, the **only** side effect is a performance hit on first access (when indexes are rebuilt).

**When to create `{type}.mgraph.json`:**
- When an issue has sub-issues (children in nested folders)
- When faster queries are needed for that subtree
- This is a business/performance decision, not a structural requirement

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    INDEX AS PERFORMANCE OPTIMIZATION                             │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   SCENARIO: All indexes deleted                                                 │
│                                                                                  │
│   Request: GET /nodes/api/feature/Feature-11/graph                              │
│                                                                                  │
│   1. Check for feature.mgraph.json → NOT FOUND                                  │
│   2. Scan folder structure, build index on-the-fly                              │
│   3. Save index for next time                                                   │
│   4. Return response                                                            │
│                                                                                  │
│   First request: 500ms (rebuild)                                                │
│   Subsequent:    5ms (cached index)                                             │
│                                                                                  │
│   This is acceptable! The system is always functional.                          │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 5. Root Node Type: Any Issue Can Be Root

**Decision:** No special `project` or `root` type needed. Any issue can serve as a root.

**Key Insight:** The UI (consumer of data) decides which parent folder to use as the entry point. This is fundamental to scalability — **every folder is self-contained**.

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                    ANY ISSUE CAN BE ROOT                                         │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                  │
│   The same data can be viewed from different entry points:                      │
│                                                                                  │
│   VIEW 1: Version as root                                                       │
│   └── Version-1/                        ◄── UI loads this as root              │
│       └── feature/Feature-11/                                                   │
│           └── task/Task-23/                                                     │
│                                                                                  │
│   VIEW 2: Feature as root                                                       │
│   └── Feature-11/                       ◄── Different UI loads this as root    │
│       └── task/Task-23/                                                         │
│                                                                                  │
│   VIEW 3: Task as root (focused work)                                           │
│   └── Task-23/                          ◄── Agent loads just this task         │
│                                                                                  │
│   Each is valid. The folder is self-contained.                                  │
│   Links to external issues work via node_id lookup in global index.             │
│                                                                                  │
└─────────────────────────────────────────────────────────────────────────────────┘
```
