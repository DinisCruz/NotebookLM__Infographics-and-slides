## The Problem

Testing the SA CloudFront Log Pipeline requires realistic log data. Today there are two options, both bad:

1. **Pull from production** — not suitable for unit tests, introduces external dependency, non-deterministic, slow
2. **Hand-craft synthetic logs** — brittle, tightly coupled to assumptions about format, easy to get wrong, doesn't scale across log types

The deeper problem is that CloudFront logs don't exist in isolation. They're the output of a chain: an HTTP request hits a CloudFront distribution (with a specific configuration), which produces a log entry, which flows through Kinesis Firehose, which writes a file to S3, which triggers a Lambda function. Testing any part of this chain in isolation means making assumptions about what the upstream parts produce — assumptions that can silently drift from reality.

What we need is a way to simulate the chain itself, so test data is **correct by construction**.

---

## The Idea: Alive Digital Twins

The project already uses the concept of digital twins — static representations of AWS infrastructure captured via boto3 and stored as Type_Safe schemas. These twins describe what exists: which CloudFront distributions, which S3 buckets, which Lambda functions, and how they're configured.

**Type__Twin extends this from static to alive.** A Type__Twin doesn't just describe a CloudFront distribution — it *behaves* like one. Feed it an HTTP request, and it produces a log entry in the same format the real service would. Feed that log entry to a Type__Twin__Firehose, and it batches and writes to a Type__Twin__S3 (backed by Memory-FS). The twin reacts to input the same way the real thing would.

### Static Twins Become Schema__Twin

The static digital twin data — previously just `Schema__` classes — gets a dedicated home in the naming hierarchy as `Schema__Twin__*`. This separates twin schemas (representations of external systems) from application schemas (representations of our own data).

The static twin splits into two distinct concerns:

| Schema | What it captures | Lifecycle | Source |
|--------|-----------------|-----------|--------|
| `Schema__Twin__Config__*` | How the service is configured | Rarely changes (deployment events) | `boto3 describe_*` |
| `Schema__Twin__State__*` | What the service looks like at runtime | Changes constantly (per-request) | Evolves during simulation |

- **Config** is what you'd capture from `boto3 describe_distribution` — origins, cache behaviours, log field selection. It changes when someone deploys a new configuration.
- **State** is what accumulates during operation — request counts, cache hit ratios, edge locations active, bytes transferred. It starts fresh each simulation run and evolves as the twin processes inputs.

The alive twin combines both:

```python
Type__Twin__CloudFront
    config : Schema__Twin__Config__CloudFront      # captured via boto3, static
    state  : Schema__Twin__State__CloudFront       # evolves during simulation

    def execute(request) -> log_entry              # the alive part
```

### State Encapsulation Rule

**In normal operation, `Schema__Twin__State` should never be modified directly.** State is an *output* of the twin's behaviour, not an input you manipulate. You always go through `Type__Twin.execute()` to evolve state — this ensures the state transitions are realistic and consistent.

**Exception: tests.** In tests, setting State directly is a legitimate escape hatch for creating specific scenarios ("what if CloudFront has already served 10,000 requests and the cache is 95% full?"). This is the same philosophy as Type_Safe itself — strict by default, with controlled ways to override when you know what you're doing.

## The Core Pattern: Typed Transformation

A `Type__Twin` is a typed transformation with configuration and state:

```
Config (Schema__Twin__Config) + State (Schema__Twin__State) + Input (Type_Safe)
    → ACTION
        → Output (Type_Safe) + Updated State
```

This is more than a pure function — pure functions are stateless. AWS services have configuration that affects their behaviour and state that accumulates. A CloudFront distribution's config (origins, cache behaviours, log field selection) determines how it transforms an HTTP request into a log entry. Its state (request count, bytes served) evolves with each request.

### Naming Rationale

**`Type__Twin`** — describes the intent (simulate a real thing), not the mechanics (input → output). Intent is the better naming choice — it tells you *why* the code exists.

**`Schema__Twin__Config` / `Schema__Twin__State`** — separates twin schemas (representations of external systems) from application schemas (our own data). Makes it immediately clear this data was captured from an external source.

**`__AWS__` in the middle** — the twin concept is cloud-agnostic. The AWS layer provides shared concepts (regions, ARNs, account IDs). `Type__Twin__Azure__*` and `Type__Twin__GCP__*` are natural extensions.

**`AWS__Twin__*`** — the intent-focused abstraction layer, analogous to what osbot-aws does for boto3. Two layers because fidelity (matching real AWS exactly) and usability (easy developer API) are different concerns that change for different reasons.

**`AWS__Twin__*__Boto3` / `AWS__Twin__*__API`** — explicit about which compatibility layer is being exposed. Boto3 for Python-native integration, API (Fast_API) for the case where real boto3 talks to the twin over HTTP.

## Composition: Chaining Twins

The real power is composition. AWS services form pipelines — CloudFront → Firehose → S3 → Lambda. Type__Twin instances compose the same way:

```
Type__Twin__AWS__CloudFront    :  Request → Log Entry
Type__Twin__AWS__Firehose      :  Log Entry → Batched File
Type__Twin__AWS__S3            :  Batched File → Stored Object (Memory-FS)
Type__Twin__AWS__Lambda        :  S3 Event → Pipeline Output
```

Each twin's output schema must match the next twin's input schema. If they don't, Type_Safe catches it at assignment time — not at runtime deep in a test.

### Pipeline Composition

```python
class Type__Twin__Pipeline(Type__Twin):                         # Chain of twins
    twins : List[Type__Twin]                                    # Ordered processing steps

    def execute(self, input_data: Type_Safe) -> Type_Safe:      # Run through chain
        result = input_data
        for twin in self.twins:
            result = twin.execute(result)
        return result

# Wire up the SA pipeline simulation
sa_pipeline = Type__Twin__Pipeline(twins = [Type__Twin__AWS__CloudFront (config = cf_config ),
                                            Type__Twin__AWS__Firehose   (config = fh_config ),
                                            Type__Twin__AWS__S3         (config = s3_config  )])
```

### Type Safety at the Seams

The composition model means schema mismatches are caught early:

```python
# If CloudFront produces a log entry with 27 fields
# but Firehose expects 28 fields
# Type_Safe catches this when the twin chain is constructed
# NOT when a test fails with a cryptic error
```

## The boto3 Interface Layer

The alive twin concept can be extended further: expose the same interface as boto3.

If `Type__Twin__AWS__S3` exposes `put_object`, `get_object`, `list_objects_v2` with the same method signatures (but Type_Safe schemas underneath and Memory-FS as the backend), then:

- Code that works against the twin works against real AWS
- Code that works against real AWS works against the twin
- You can swap between twin and real via configuration, not code changes

```python
class Type__Twin__AWS__S3(Type__Twin__AWS):                     # S3-compatible interface
    config  : Schema__Twin__Config__AWS__S3
    state   : Schema__Twin__State__AWS__S3
    storage : Storage_FS                                        # Memory-FS backend

    def put_object(self, Bucket: Safe_Str, Key: Safe_Str,       # Same signature as boto3
                         Body: bytes) -> Schema__S3__Response:
        self.storage.save(key=Key, data=Body)
        self.state.total_objects += 1                           # State evolves
        return Schema__S3__Response(status=200)

    def get_object(self, Bucket: Safe_Str, Key: Safe_Str        # Same signature as boto3
              ) -> Schema__S3__GetObject__Response:
        data = self.storage.load(key=Key)
        self.state.total_reads += 1                             # State evolves
        return Schema__S3__GetObject__Response(Body=data)
```

This closes the loop with the existing `osbot-aws` abstraction layer — where `osbot-aws` wraps boto3, `Type__Twin__AWS__S3` replaces it for testing with identical semantics.

## Serialisation and Storage via Memory-FS

One of the most powerful properties of this architecture comes for free from Type_Safe: **automatic serialisation**.

Every `Schema__Twin__Config`, `Schema__Twin__State`, and every input/output flowing through the system supports `.json()` and `.from_json()` round-trips. This means the entire twin environment — config, state, and execution history — can be serialised and stored.

Memory-FS provides the storage abstraction, which can be backed by:

| Backend | Use Case |
|---------|----------|
| **In-memory** | Unit tests (fast, ephemeral) |
| **Zip file** | Snapshot a twin environment for sharing or replay |
| **SQLite** | Persistent local twin state across test runs |
| **S3 / Cloud storage** | Shared twin environments across CI/CD pipelines |

This means you can:

1. **Snapshot** a twin mid-simulation (`state.json()` → Memory-FS)
2. **Restore** from a snapshot to reproduce a specific scenario (`State.from_json()`)
3. **Share** twin environments between developers or CI runs
4. **Version** twin configs alongside code (they're just JSON files)

## Cross-Cloud Simulation

Because `Type__Twin` and `Schema__Twin` are cloud-agnostic base classes, with `__AWS__` as just one specialisation, the architecture naturally extends to other cloud providers:

```
Type__Twin
├── Type__Twin__AWS
│   ├── Type__Twin__AWS__S3
│   ├── Type__Twin__AWS__CloudFront
│   └── Type__Twin__AWS__Lambda
├── Type__Twin__Azure
│   ├── Type__Twin__Azure__Blob_Storage
│   ├── Type__Twin__Azure__CDN
│   └── Type__Twin__Azure__Functions
└── Type__Twin__GCP
    ├── Type__Twin__GCP__Cloud_Storage
    ├── Type__Twin__GCP__Cloud_CDN
    └── Type__Twin__GCP__Cloud_Functions
```

The Type_Safe schemas don't care where they're serialised. Memory-FS doesn't care if it's ultimately backed by S3 or Azure Blob Storage. This means:

- **Simulate AWS from inside Azure** — run your AWS twin pipeline in an Azure-hosted CI environment
- **Simulate Azure from inside AWS** — test Azure migration without an Azure account
- **Compare cloud behaviours** — "how would this pipeline behave if we moved from CloudFront to Azure CDN?"

The twins for different clouds would share common interface patterns (CDN twin, object storage twin, serverless function twin) while implementing cloud-specific behaviours and configuration schemas.

## IAM Simulation: Where It Gets Transformative

IAM is notoriously difficult to understand, test, and audit. The current reality: you make a change to an IAM policy, deploy it, and hope nothing breaks. If something does break, you're debugging permission errors in production.

A `Type__Twin__AWS__IAM` changes this entirely. Per the 100% fidelity principle, the IAM twin must match real AWS policy evaluation exactly — including known quirks, edge cases, and the specific precedence rules for explicit deny vs. allow vs. implicit deny:

```python
class Schema__Twin__Config__AWS__IAM(Schema__Twin__Config__AWS):
    policies    : Dict__IAM__Policies__By_ARN                   # All policies
    roles       : Dict__IAM__Roles__By_ARN                      # All roles
    users       : Dict__IAM__Users__By_ARN                      # All users
    groups      : Dict__IAM__Groups__By_ARN                     # All groups
    boundaries  : Dict__IAM__Permission__Boundaries             # Permission boundaries

class Type__Twin__AWS__IAM(Type__Twin__AWS):                    # Fidelity layer: exact AWS behaviour
    config : Schema__Twin__Config__AWS__IAM

    def evaluate_policy(self, principal  : Safe_Str ,           # Who is making the request
                              action     : Safe_Str ,           # What they want to do
                              resource   : Safe_Str             # What they want to do it to
                   ) -> Schema__IAM__Evaluation__Result:        # Allow / Deny / Implicit Deny
        # Replicate the IAM policy evaluation logic EXACTLY:
        # 1. Check identity-based policies
        # 2. Check resource-based policies
        # 3. Check permission boundaries
        # 4. Check SCPs (if in an Organization)
        # 5. Evaluate Allow/Deny with correct precedence
        # INCLUDING known AWS quirks and edge cases
        pass

class AWS__Twin__IAM(AWS__Twin):                                # Intent layer: easy to use
    twin : Type__Twin__AWS__IAM

    def can_access(self, who: str, what: str,                   # Simple question
                         resource: str) -> bool:
        pass

    def what_if_remove_policy(self, policy_arn: str             # Impact analysis
                         ) -> List[Schema__IAM__Impact]:
        pass

    def who_can_access(self, resource: str                      # Posture query
                  ) -> List[Schema__IAM__Principal]:
        pass
```

With the `AWS__Twin__IAM` intent layer, you can:

- **Audit before deploy:** "If I remove this policy, which services lose access?"
- **Test permission changes:** Run your entire twin pipeline with a proposed IAM change and see what breaks
- **Understand your posture:** "Which principals can access this S3 bucket?" — answered locally, in milliseconds
- **Detect drift:** Compare the twin's IAM config (captured via boto3) against your intended state
- **Onboard developers:** "Here's a twin of our AWS environment — explore it without touching production"

The IAM twin would be seeded from real AWS data via `boto3 get_policy`, `get_role`, `list_attached_role_policies`, etc. — all captured as `Schema__Twin__Config__AWS__IAM` and stored in the repo as JSON via the Type_Safe round-trip.

## Verification Against Reality

A core principle: **every `Type__Twin__AWS__*` class must match 100% of the real AWS behaviour for what it supports — including bugs and quirks.** The twin is not an idealised version of AWS; it's a mirror.

Twins are verified against real AWS data:

```python
# 1. Capture real data via boto3
real_logs     = s3_client.get_object(Bucket='prod-logs', Key='2026/02/17/...')

# 2. Simulate the same scenario
simulated_log = twin_cloudfront.execute(same_request)

# 3. Compare structure and field presence
assert set(real_log.fields()) == set(simulated_log.fields())

# 4. Compare value distributions (not exact values)
assert simulated_log.sc_status in real_status_distribution
```

This is the "trust but verify" model — the twin is the primary source for tests, but periodic comparison against real AWS data ensures the twin hasn't drifted.

### When AWS Changes Behaviour

When AWS changes its behaviour, that's just a different tag (or branch) in the repo. The twin config and implementation are versioned alongside everything else:

```
git tag aws-twin/v2025.12                                       # AWS behaviour as of Dec 2025
# ... AWS makes a change ...
git tag aws-twin/v2026.01                                       # AWS behaviour after Jan 2026 change
```

This creates powerful capabilities:

**Replay past behaviour:** Check out an older tag and run tests against the AWS behaviour as it was at that point in time. Diff the results to see exactly what an AWS change broke.

**Migration safety net:** When AWS announces a breaking change, create a branch with the new twin behaviour, run the full test suite, see what breaks, fix it, and verify — all before the real change goes live.

**Abstraction layer for stability:** For teams where AWS changes frequently break things, `AWS__Twin__*` can absorb the change at the intent layer while `Type__Twin__AWS__*` faithfully replicates the new behaviour. Application code doesn't change. This is the same pattern as osbot-aws, but now it's testable, simulatable, and version-controlled.

## Resolved Decisions

1. **Naming is final.** `Type__Twin` is the name. No further discussion needed.

2. **No special test API for state manipulation.** State should always be modified through `execute()`, even in tests. The goal is to push all state changes through the simulation so they replicate real AWS behaviour. If a test needs specific state, it should replay the sequence of inputs that produces that state — this ensures the state transitions are realistic. Edge cases where direct state access is truly needed can use normal Type_Safe attribute access, but this should be rare and explicit.

3. **Twin configs stored in the repo.** App-specific twins (the `Schema__Twin__Config__AWS__*` instances for your actual AWS environment) are stored in the repo alongside the code. Just like `.issues` files (via Issues-FS) represent the work this codebase is related to, twin configs represent the infrastructure this codebase runs on. They are the single source of truth for "what does our AWS environment look like." This has a powerful secondary property: **these stored configs could be used to generate CloudFormation stacks or Terraform scripts.** The twin config IS the infrastructure definition, just in a Type_Safe format that's also executable as a simulation.

4. **Organic scope, focused on need.** We only add the methods and functionality required by the current project. The Type__Twin base classes provide the framework; implementations grow organically as we need them. The project is Open Source — others can extend and submit PRs for services we haven't reached yet.

5. **100% fidelity to real AWS behaviour for what is supported.** Every `Type__Twin__AWS__*` class must match the real AWS service exactly — including bugs and gaps. If AWS has a known quirk (e.g., S3 eventual consistency in certain operations, IAM policy evaluation edge cases), the twin replicates it. The twin is not an idealised version of AWS; it's a mirror. When AWS changes behaviour, that's a new version tag in the repo — see "Verification Against Reality" for how this enables replay, migration testing, and stability abstraction.

## Additional Architecture: The AWS__Twin Abstraction Layer

The `Type__Twin__AWS__*` classes described above are the **low-level simulation layer** — they match real AWS behaviour exactly, warts and all. On top of this, we add a separate abstraction layer focused on usability.

### Two Layers

```
┌─────────────────────────────────────────────────────┐
│  AWS__Twin / AWS__Twin__*                           │  Intent-focused, easy to use
│  "create a distribution", "invoke a function"       │  (like osbot-aws for the twin)
├─────────────────────────────────────────────────────┤
│  Type__Twin__AWS / Type__Twin__AWS__*                │  Fidelity-focused, matches real AWS
│  "replicate exact CloudFront log format"            │  (including bugs and quirks)
└─────────────────────────────────────────────────────┘
```

| Layer | Focus | API Style | Example |
|-------|-------|-----------|---------|
| `Type__Twin__AWS__*` | **Fidelity** — matches real AWS exactly | Low-level, mirrors AWS internals | `twin.execute(request)` → log entry with exact field format |
| `AWS__Twin__*` | **Intent** — easy to use | High-level, human-readable methods | `aws_twin.create_distribution(origins=[...])` |

This mirrors the relationship between boto3 (low-level AWS API wrapper) and osbot-aws (intent-focused abstraction). The key difference: `Type__Twin__AWS__*` is the simulation engine, `AWS__Twin__*` is the developer experience layer.

### Full Stack Example

```python
# Set up an AWS twin environment
aws = AWS__Twin__Environment()                                  # Wires everything together

# Create infrastructure (intent-focused)
aws.cloudfront.create_distribution(origins=['api.example.com'])
aws.s3.create_bucket('my-logs')

# Simulate traffic
for i in range(100):
    aws.cloudfront.simulate_request(path=f'/api/endpoint-{i % 5}')

# The twin has now generated 100 realistic log entries,
# batched them through Firehose, written them to S3 (Memory-FS),
# and they're ready for the LETS pipeline to process
```

## boto3 and REST API Compatibility

The ultimate goal is that application code cannot tell the difference between talking to real AWS and talking to the twin. This requires API compatibility at two levels:

### Level 1: boto3-Compatible Interface

```python
class AWS__Twin__S3__Boto3(AWS__Twin__S3):                      # boto3 method signatures
    def put_object(self, Bucket, Key, Body, **kwargs):          # Exact boto3 signature
        return self.twin.execute(...)

    def get_object(self, Bucket, Key, **kwargs):                # Exact boto3 signature
        return self.twin.execute(...)

    def list_objects_v2(self, Bucket, Prefix='', **kwargs):     # Exact boto3 signature
        return self.twin.execute(...)
```

### Level 2: REST API via Fast_API

Since boto3 is fundamentally a wrapper on top of the AWS REST API, the twin can also expose a Fast_API application that implements the same REST endpoints:

```python
class AWS__Twin__S3__API(Type_Safe):                            # REST API matching AWS S3 API
    twin : Type__Twin__AWS__S3                                  # Backed by the simulation

    # Registers routes matching AWS S3 REST API:
    # PUT /{bucket}/{key}     → put_object
    # GET /{bucket}/{key}     → get_object
    # GET /{bucket}?list-type=2  → list_objects_v2
```

This means you could point actual boto3 (the real library) at the twin's Fast_API endpoint and it would work — boto3 sends HTTP requests, the twin API handles them, the simulation runs, and boto3 gets back responses in the format it expects.

### Naming Pattern for API Layers

| Class | What it does |
|-------|-------------|
| `Type__Twin__AWS__S3` | Fidelity simulation engine |
| `AWS__Twin__S3` | Intent-focused developer API |
| `AWS__Twin__S3__Boto3` | boto3-compatible method signatures |
| `AWS__Twin__S3__API` | Fast_API REST endpoint matching AWS API |
