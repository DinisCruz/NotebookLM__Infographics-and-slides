# Brief: Tables as Graphs — Everything Is a Graph, the Question Is How to Store It

**version** v0.4.11  
**date** 19 Feb 2026  
**from** Human (project lead)

**type** Research brief — architectural philosophy

## The Thesis

**Everything can be represented as a graph.** This is not a metaphor. It's a statement about the nature of data.

A table is a graph. A CSV file is a graph. A spreadsheet is a graph. A Postgres database is a graph. A text file containing "Hello world" is a graph (text node → words → characters → encodings — multiple nodes at multiple levels of abstraction). The question is never "is this data a graph?" — it always is. The question is:

**What is the most optimal and efficient way/technology/medium to store, retrieve, edit, visualise, and version control this graph?**

That question has different answers depending on the use case. Sometimes the answer is a native graph database. Sometimes it's a relational SQL database. Sometimes it's a flat file. Sometimes it's a spreadsheet. The data is still a graph regardless of what the storage medium calls it or what its users, designers, or builders think it is.

## A Table Is a Graph

Take any table — a database table, a spreadsheet, a CSV. Here's the graph structure hiding inside it:

```
Table
├── has-rows → Rows (collection node)
│   ├── has-row → Row-1
│   │   ├── has-cell → Cell-1-A (value: "Acme Corp")
│   │   ├── has-cell → Cell-1-B (value: "Invoice")
│   │   └── has-cell → Cell-1-C (value: "£5,000")
│   ├── has-row → Row-2
│   │   ├── has-cell → Cell-2-A (value: "Acme Corp")
│   │   ├── has-cell → Cell-2-B (value: "Payment")
│   │   └── has-cell → Cell-2-C (value: "£3,000")
│   └── has-row → Row-3
│       ├── has-cell → Cell-3-A (value: "Beta Ltd")
│       ├── has-cell → Cell-3-B (value: "Invoice")
│       └── has-cell → Cell-3-C (value: "£8,000")
└── has-columns → Columns (collection node)
    ├── has-column → Column-A ("Company")
    │   ├── has-cell → Cell-1-A
    │   ├── has-cell → Cell-2-A
    │   └── has-cell → Cell-3-A
    ├── has-column → Column-B ("Type")
    └── has-column → Column-C ("Amount")
```

The cell is the intersection of row and column — it's a node with edges to both. The table is the root node. Everything is nodes and edges.

### The Non-Unique Node Problem

In a table, "Acme Corp" exists as a string in Cell-1-A and Cell-2-A. These are two separate cells containing the same text. The table has duplicated the data.

In a native graph, "Acme Corp" would be a single node with two edges (one to Row-1, one to Row-2). No duplication. The relationship is explicit.

### What Is an Index?

An index is the table's way of recovering the graph's natural deduplication:

```
Table
└── has-indexes → Indexes
    └── has-index → Index-Company
        ├── has-entry → "Acme Corp" (unique node)
        │   ├── points-to → Cell-1-A
        │   └── points-to → Cell-2-A
        └── has-entry → "Beta Ltd" (unique node)
            └── points-to → Cell-3-A
```

An index is a new subgraph that creates unique nodes for repeated values and links them back to the cells where those values appear. It's a graph structure that retroactively adds the relationship optimisation that a native graph has by default.

**A table is a graph optimised for retrieval, not for relationships.** Indexes are the mechanism for recovering relationship capability when you need it.

## The Pragmatic Question

Given that everything is a graph, the question becomes: **what's the best storage medium for this particular graph?**

| Storage Medium | Optimised For | Trade-Offs |
|---|---|---|
| **Native graph DB** (Neo4j, etc.) | Relationship traversal, multi-hop queries, connectivity analysis | Worse at bulk retrieval, less familiar to most users |
| **Relational DB** (Postgres, SQLite) | Indexed retrieval, aggregation, structured queries | Worse at deep relationship traversal, schema-heavy |
| **Flat files** (.issues, .md, .json) | Human readability, version control (git), simplicity, low friction | No query engine, limited scale |
| **Spreadsheets** (CSV, XLSX, Google Sheets) | Visual editing, familiar to non-developers, collaborative | Poor version control, limited programmability |
| **Key-value stores** | Fast lookup by key, caching | No relationships, no traversal |

The answer is often: **use what exists, what users are already comfortable with, and what is realistic.** The key is to make sure we can link into it — that whatever storage medium is used, the data can be connected to the wider graph.

A relational SQL database could be the best choice for a given use case. The data stored in that database is still a graph — regardless of whether that's what it's called internally or what its users, designers, or builders think it is. The important thing is not that everything is stored in a graph database. The important thing is that everything can be *understood* as a graph and *connected* as a graph.

## Issues-FS Already Does This: The .issues Format as Proof

The `.issues` flat file format (v0.6.1) is a concrete example of this philosophy in action. Look at what it actually is:

```
Workstream-1 | in-progress | Observability
	Task-1 | done | CloudFront logs
	Task-2 | in-progress | S3 logging
	Task-3 | todo | Dashboards
```

This looks like a table. It IS a quasi-table — pipe-delimited, one record per line, with columns (label, status, description). A human reads it like a table. An editor edits it like a table.

But underneath, it's a graph:

```
Workstream-1 (status: in-progress, description: "Observability")
├── has-task → Task-1 (status: done, description: "CloudFront logs")
├── has-task → Task-2 (status: in-progress, description: "S3 logging")
└── has-task → Task-3 (status: todo, description: "Dashboards")
```

The tab indentation creates parent-child edges (`has-task`). The `->` syntax creates cross-reference edges (`relates-to`). The label prefix determines the node type. The status determines the node state. The `Graph__Repository` discovers these files and integrates them into the full graph — `nodes_list_all()` includes them seamlessly.

**The user operates in table mode. The system stores and connects in graph mode.** This is the design principle.

## The Extension Path: CSV, XLSX, Google Sheets, Airtable

The `.issues` format proves the pattern. Now extend it:

### CSV Files

A CSV file is structurally almost identical to a `.issues` file — pipe-delimited becomes comma-delimited. The mapping is direct:

```csv
Label,Status,Description,Parent
Task-1,done,CloudFront logs,Workstream-1
Task-2,in-progress,S3 logging,Workstream-1
Task-3,todo,Dashboards,Workstream-1
```

Every row becomes a node. Column headers define the properties. A "Parent" or "Relates-To" column defines edges. The CSV is the table view. The graph is the underlying structure.

**Implementation**: a CSV loader that reads any CSV, maps rows to nodes, maps designated columns to edges, and integrates into the `Graph__Repository`. Convention-based: if a column name matches a known label pattern (e.g., contains a value like "Task-1"), it's an edge.

### XLSX Files

Same as CSV but with multiple sheets. Each sheet could be:
- A different workstream
- A different node type (one sheet for tasks, one for bugs, one for risks)
- A different projection of the same graph

**Implementation**: extend the CSV loader to handle XLSX. Each sheet is processed independently. Cross-sheet references (a cell in Sheet A containing a label from Sheet B) become cross-graph edges.

### Google Sheets

Same as XLSX but live and collaborative. The graph syncs with the sheet:
- Edit a cell in Google Sheets → the graph node updates
- Add a row → a new node appears in the graph
- The graph can also write back → update a status in the graph, the sheet reflects it

**Implementation**: Google Sheets API integration. Poll for changes or use push notifications. Map rows ↔ nodes, designated columns ↔ edges. The sheet becomes a live view of a subgraph.

### Airtable

Airtable is already closer to a graph than a spreadsheet — it has linked records, which are explicit edges between rows in different tables. The mapping is natural:
- Airtable table → node type
- Airtable row → node
- Airtable linked record field → edge
- Airtable view → projection

**Implementation**: Airtable API integration. The linked record structure maps almost 1:1 to graph edges.

### The Common Pattern

In every case, the pattern is the same:

```
User operates in familiar medium (spreadsheet, CSV, flat file)
        ↕ bidirectional sync
Issues-FS stores and connects as graph
        ↕ bidirectional sync
Other systems consume the graph (queries, visualisations, APIs)
```

The user never has to think about graphs. They work in whatever tool they're comfortable with. Issues-FS handles the graph representation underneath and ensures everything is connected.

## Projections: Graph → Table and Table → Graph

The bidirectional conversion is key:

### Table → Graph (Import/Ingestion)

Take any table (CSV, XLSX, database query result, Google Sheet) and convert it to a graph:
- Each row → a node
- Column headers → property names
- Designated columns → edges to other nodes
- The table itself → a container node

This is what the `.issues` loader already does. Extend it to any tabular format.

### Graph → Table (Export/Projection)

Take any subgraph and project it into a table:
- Select a node type → each node becomes a row
- Select properties → each property becomes a column
- Select edge types → follow edges and include target node properties as columns
- Output as CSV, XLSX, or write to a Google Sheet

**Why projections matter**: tables are how people consume data. Reports, dashboards, summaries — they're all tables. The graph is the storage and relationship layer. The table is the presentation layer. The projection is the bridge.

The human has done this in practice — taking native graph structures (nodes and edges) and converting them into spreadsheet format for consumption. The data doesn't change. The representation changes based on how it will be used.

## Graphs of Graphs of Graphs

This is where the fractal philosophy scales:

```
Issues-FS Graph (nodes from .issues files, JSON, etc.)
    ↕ connects to
Memory-FS Graph (cached data, computed relationships)
    ↕ connects to
Graph-DB Graph (persistent storage, query optimisation)
    ↕ connects to
External Data (Google Sheets, Airtable, SQL databases, CSV files)
```

Each system stores its graph in the medium that makes sense for its use case:
- Issues-FS: flat files (human-readable, git-versioned)
- Memory-FS: in-memory (fast access, computed properties)
- Graph-DB: persistent database (query optimisation, scale)
- External: whatever the user already uses (spreadsheets, databases, Airtable)

The graphs connect. A node in Issues-FS can reference a node in Graph-DB. A row in Google Sheets can be a node that edges to an issue in a `.issues` file. The graph of graphs is the meta-structure that connects everything.

**The pragmatism**: we don't ask users to change their tools. We link into what they already use. The graph is the connective tissue, not the mandated storage format.

## The Real Question We Should Always Be Asking

For every piece of data, every system, every storage decision:

> **What is the most optimal and efficient way to store, retrieve, edit, visualise, and version control this data?**

Sometimes the answer is a `.issues` flat file. Sometimes it's a Postgres table. Sometimes it's a Google Sheet. Sometimes it's a native graph database. Sometimes it's all of these simultaneously, with the graph layer connecting them.

The answer depends on:

| Dimension | Table-Optimised | Graph-Optimised | File-Optimised |
|---|---|---|---|
| **Store** | Structured, typed, schema-enforced | Flexible, schema-optional | Human-readable, portable |
| **Retrieve** | Fast indexed lookup | Fast relationship traversal | Simple file read |
| **Edit** | SQL / spreadsheet UI | Graph mutations | Text editor / git |
| **Visualise** | Tables, charts, dashboards | Network diagrams, trees | Rendered markdown |
| **Version control** | DB migrations, audit logs | Graph diffs | Git (perfect fit) |

The `.issues` format optimises for: edit (text editor), version control (git), and human readability — while still being a graph underneath. That's the sweet spot for our use case. Other use cases have different sweet spots.
