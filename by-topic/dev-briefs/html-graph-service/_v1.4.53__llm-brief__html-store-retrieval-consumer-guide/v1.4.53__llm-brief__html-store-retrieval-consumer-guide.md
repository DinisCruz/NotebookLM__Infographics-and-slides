## 1. Introduction

### 1.1 Why This Exists

Modern web applications often need to:
- **Cache HTML pages** for performance, offline access, or transformation
- **Track multiple versions** of the same page over time
- **Transform HTML** before serving (e.g., content filtering, ad removal, accessibility enhancements)
- **Observe and debug** HTML processing pipelines
- **Decouple HTML capture from HTML consumption** (different services, different times)

The HTML Store & Retrieval system provides a **unified, observable, versioned** approach to HTML caching that works seamlessly across REST APIs and internal services.

### 1.2 What It Provides

| Capability | Description |
|------------|-------------|
| **Multi-mode Storage** | Store HTML from raw content, URLs, or explicit cache keys |
| **Flexible Retrieval** | Load HTML by cache_id, cache_hash, cache_key, or URL |
| **Automatic Versioning** | Same cache_key can have multiple versions (different cache_ids) |
| **Built-in Observability** | Every operation records flow data, logs, tasks, and durations |
| **Storage Abstraction** | Uses Cache Service behind the scenes (location-agnostic) |
| **Entity-Centric Model** | Each "page" is an entity that can hold multiple data files |

### 1.3 How It Works (High-Level)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           HTML Store & Retrieval                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   ┌─────────────┐     ┌─────────────┐     ┌─────────────────────────────┐   │
│   │   Store     │     │    FLeT     │     │      Cache Service          │   │
│   │  HTML from  │────▶│  Pipeline   │────▶│  (Entity + Data Files)      │   │
│   │ URL/Raw/Key │     │ (Observable)│     │                             │   │
│   └─────────────┘     └─────────────┘     └─────────────────────────────┘   │
│                                                    │                         │
│   ┌─────────────┐     ┌─────────────┐              │                         │
│   │   Load      │     │    FLeT     │              │                         │
│   │  HTML by    │◀────│  Pipeline   │◀─────────────┘                         │
│   │ ID/Hash/Key │     │ (Observable)│                                        │
│   └─────────────┘     └─────────────┘                                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Key Concept**: Every HTML page becomes an **entity** in the Cache Service. The HTML content is stored as a **data file** within that entity. This separation allows:
- Multiple data files per entity (raw HTML, transformed HTML, metadata, etc.)
- Entity-level metadata and references
- Version tracking via cache_hash

## 2. Core Concepts

### 2.1 The Page Entity Model

Each cached HTML page is represented as a **Cache Entity** with the following structure:

```
Entity (Page)
├── cache_id       : Unique identifier (e.g., "a1b2c3d4e5f6")
├── cache_key      : Human-readable key (e.g., "sites/example.com/pages/about")
├── cache_hash     : Content-based hash for deduplication
├── metadata       : Entity-level metadata
├── refs           : References (by-id, by-hash indexes)
└── data/          : Data files folder
    ├── html/raw.txt           : Original HTML content
    ├── html/transformed.txt   : Transformed HTML (optional)
    ├── meta/info.json         : Page metadata (optional)
    └── flows/html-to-cache/   : FLeT execution data
```

### 2.2 Storage Location Examples

When you store HTML, it gets saved in a hierarchical structure:

**Example 1: Store by URL**
```
URL: https://example.com/about

Cache Key: sites/example.com/pages/about
Storage Path: {namespace}/data/key-based/sites/example.com/pages/about/root/data/html/raw.txt
```

**Example 2: Store by explicit key**
```
Cache Key: my-app/pages/landing-v2

Storage Path: {namespace}/data/key-based/my-app/pages/landing-v2/root/data/html/raw.txt
```

**Example 3: Store raw HTML (auto-generated key)**
```
Cache Key: html/raw/{content-hash}

Storage Path: {namespace}/data/key-based/html/raw/{hash}/root/data/html/raw.txt
```

### 2.3 Data Key and File ID

Within each entity, data files are organized by `data_key` and `data_file_id`:

| Parameter | Purpose | Example |
|-----------|---------|---------|
| `data_key` | Folder path within entity | `html`, `html/content`, `meta` |
| `data_file_id` | File name (without extension) | `raw`, `transformed`, `info` |

**Common patterns:**
- `data_key='html', data_file_id='raw'` → Original HTML
- `data_key='html', data_file_id='transformed'` → Processed HTML
- `data_key='meta', data_file_id='info'` → JSON metadata

### 3.5 Complete REST API Workflow Example

```python
import requests

BASE_URL = "https://html-graph.dev.mgraph.ai"
NAMESPACE = "my-proxy-app"

# 1. Store HTML from URL
response = requests.post(
    f"{BASE_URL}/flet-html-domain/html/store/{NAMESPACE}/url",
    json={"url": "https://news.ycombinator.com"}
)
result = response.json()
cache_id = result["cache_id"]
cache_key = result["cache_key"]

print(f"Stored: cache_id={cache_id}, cache_key={cache_key}")

# 2. Later, load by cache_id
response = requests.post(
    f"{BASE_URL}/flet-html-domain/html/load/{NAMESPACE}/id",
    json={"cache_id": cache_id}
)
html = response.json()["html"]

# 3. Or load by URL (same result)
response = requests.post(
    f"{BASE_URL}/flet-html-domain/html/load/{NAMESPACE}/url",
    json={"url": "https://news.ycombinator.com"}
)

# 4. Check execution flows
response = requests.get(
    f"{BASE_URL}/flet-flows/flows/{NAMESPACE}/{cache_id}"
)
print(f"FLeTs executed: {response.json()['flets']}")
```

## 5. MVP Use Case: MitmProxy Passive Mode

### 5.1 Scenario

A MitmProxy instance operates in **passive mode**:
1. **First request** to a page → Fetch from origin, **save HTML to cache**, return original
2. **Subsequent requests** to same page → **Load HTML from cache**, optionally transform

This enables:
- **Caching without explicit user action**
- **Optional transformation** (content filtering, ad removal, etc.)
- **Offline access** to previously visited pages
- **Version tracking** of page changes over time

### 5.2 Implementation Pattern

```python
class MitmProxyHtmlHandler:
    
    def __init__(self, cache_client: Html_Cache__Client):
        self.domain_service = FLeT__Html__Domain__Service(cache_client=cache_client)
        self.namespace      = "mitmproxy-cache"
        self.transform_mode = False  # Set via configuration
    
    def handle_request(self, url: str) -> str:
        # 1. Check if we have this URL cached
        load_request = Schema__Html__Load__Url__Request(url=url)
        load_result  = self.domain_service.load_by_url(namespace=self.namespace, 
                                                       request=load_request)
        
        if load_result.found:
            # 2a. Cache HIT - return cached (optionally transformed)
            html = load_result.html
            if self.transform_mode:
                html = self.transform_html(html)
            return html
        else:
            # 2b. Cache MISS - fetch, store, return original
            html = self.fetch_from_origin(url)
            
            store_request = Schema__Html__Store__Url__Request(url=url)
            # Note: For this pattern, we'd store the fetched HTML with the URL as key
            store_result = self.domain_service.store_with_key(
                namespace = self.namespace,
                cache_key = self.url_to_cache_key(url),
                request   = Schema__Html__Store__Key__Request(html=html)
            )
            
            return html
    
    def transform_html(self, html: str) -> str:
        # Apply transformations (content filtering, etc.)
        # This could be another FLeT in the future!
        return html
    
    def url_to_cache_key(self, url: str) -> str:
        # Use Url__To__Cache_Key utility
        from mgraph_ai_service_html_graph.utils.Url__To__Cache_Key import Url__To__Cache_Key
        converter = Url__To__Cache_Key()
        return converter.cache_key(url)
```

### 5.3 Configuration Options

| Setting | Description | Default |
|---------|-------------|---------|
| `namespace` | Isolates this proxy's cache from others | `mitmproxy-cache` |
| `transform_mode` | Whether to transform cached HTML before returning | `False` |
| `cache_ttl` | How long to consider cache valid (future enhancement) | `None` (forever) |
| `include_query_params` | Whether URL query params affect cache key | `False` |

### 5.4 Benefits

1. **Zero-config caching**: Every page visited is automatically cached
2. **Transparent to user**: Same URL returns cached content seamlessly
3. **Transformation ready**: Easy to add content filtering in future
4. **Observable**: All cache operations tracked via FLeT flows
5. **Versioned**: Re-visiting a changed page creates new version (same cache_key, new cache_id)

## 6. Advanced Patterns

### 6.1 Multiple HTML Versions Per Entity

Store different versions of HTML in the same entity:

```python
# Store original
execute_service.execute_to_cache(
    namespace = "my-service",
    cache_id  = cache_id,
    request   = Schema__FLeT__Html__To__Cache__Request(
        html         = original_html,
        data_key     = "html",
        data_file_id = "raw"
    )
)

# Store transformed version
execute_service.execute_to_cache(
    namespace = "my-service",
    cache_id  = cache_id,
    request   = Schema__FLeT__Html__To__Cache__Request(
        html         = transformed_html,
        data_key     = "html",
        data_file_id = "transformed"
    )
)

# Load specific version
from_request = Schema__FLeT__Html__From__Cache__Request(
    data_key     = "html",
    data_file_id = "transformed"  # or "raw" for original
)
result = execute_service.execute_from_cache(namespace="my-service", 
                                            cache_id=cache_id, 
                                            request=from_request)
```

### 6.2 Namespace Isolation

Use namespaces to isolate different applications or environments:

```python
# Different apps, same cache service
domain_service.store_raw(namespace="app-a", request=request)
domain_service.store_raw(namespace="app-b", request=request)

# Different environments
domain_service.store_raw(namespace="prod-cache", request=request)
domain_service.store_raw(namespace="dev-cache", request=request)
```

### 6.3 URL to Cache Key Conversion

For consistent URL-based caching:

```python
from mgraph_ai_service_html_graph.utils.Url__To__Cache_Key           import Url__To__Cache_Key

    include_query_params = True,
```

## 8. Error Handling

### 8.1 REST API Errors

| Status Code | Meaning | Action |
|-------------|---------|--------|
| 200 | Success | Process response |
| 400 | Bad request (empty HTML, invalid URL) | Check request body |
| 404 | Entity not found | Handle cache miss |
| 500 | Server error | Retry or fallback |

### 8.2 Service-Level Handling

```python
result = domain_service.store_from_url(namespace, request)

if not result.success:
    # Store failed (invalid URL, fetch error, etc.)
    handle_error()
    
result = domain_service.load_by_id(namespace, request)

if result.success and not result.found:
    # Cache miss - entity doesn't exist or has no HTML
    fetch_and_store()
```
