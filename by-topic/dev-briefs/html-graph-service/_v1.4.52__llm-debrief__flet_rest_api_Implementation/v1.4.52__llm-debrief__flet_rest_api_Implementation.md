## 4. Key Technical Details

### 4.1 Safe Type Mappings

| Field | Safe Type |
|-------|-----------|
| `cache_id` | `Cache_Id` |
| `cache_key` | `Safe_Str__Cache__File__Cache_Key` |
| `cache_hash` | `Safe_Str__Cache__File__Cache_Hash` |
| `namespace` | `Safe_Str__Cache__Namespace` |
| `data_key` | `Safe_Str__Cache__File__Data_Key` |
| `data_file_id` | `Safe_Str__Cache__File__File_Id` |
| `flet_name` | `Safe_Str__FLeT__Name` |

### 4.2 Entity Creation Semantics

The `Cache__Entity__Service.create()` method **always creates a new entity** (no get-or-create):

```python
result_1 = service.create(namespace, request)  # cache_id = "abc123", created = True
result_2 = service.create(namespace, request)  # cache_id = "def456", created = True (different!)

# Both share same cache_hash, tracked in by-hash file:
# cache_hash → [cache_id_1, cache_id_2]
```

This enables **versioning** where multiple entities can have the same `cache_key` but different `cache_id`.

### 4.3 URL to Cache Key Conversion

```python
converter = Url__To__Cache_Key()

# Basic conversion
converter.cache_key("https://example.com/about")
# → "sites/example.com/pages/about"

# With query params
config = Schema__Url__Cache_Key__Config(include_query_params=True)
converter = Url__To__Cache_Key(config=config)
converter.cache_key("https://example.com/search?q=test")
# → "sites/example.com/pages/search/q-a1b2c3d4e5f6"

# Exclude tracking params
config = Schema__Url__Cache_Key__Config(
    include_query_params = True,
    exclude_params       = ['utm_source', 'fbclid']
)
```

### 4.4 Test Pattern

All tests use real objects via `create_html_cache_client()`:

```python
class test_Cache__Entity__Service(TestCase):

    @classmethod
    def setUpClass(cls):
        cls.html_cache_client, cls.cache_service = create_html_cache_client()
        cls.entity_service = Cache__Entity__Service(cache_client=cls.html_cache_client)
        cls.namespace      = 'test-cache-entity-service'
        cls.create_test_data()

    @classmethod
    def create_test_data(cls):
        cls.cache_key   = f'test/entity/{Random_Guid()}'
        create_request  = Schema__Entity__Create__Request(cache_key=cls.cache_key)
        create_result   = cls.entity_service.create(namespace=cls.namespace, request=create_request)
        cls.cache_id    = create_result.cache_id
        cls.test_entity = Cache__Entity(cache_client = cls.html_cache_client.cache_client,
                                        cache_id     = cls.cache_id,
                                        namespace    = cls.namespace)
```

## 8. Lessons Learned

### 8.1 Cache Client Storage Abstraction

The `mgraph_ai_service_cache_client` abstracts the storage location completely. Although tests use the **in-memory** option for speed, switching to a **REST-based** backend (e.g., https://cache.dev.mgraph.ai) requires only setting environment variables:

```python
# Tests use in-memory (fast, isolated)
cls.html_cache_client, cls.cache_service = create_html_cache_client()

# Production uses REST backend - same code, different config via env vars
# All cache client calls transparently go to the live server
```

This means the same service code works unchanged across:
- Unit tests (in-memory)
- Integration tests (local cache service)
- Production (remote cache service)

### 8.2 Entity Pre-Creation and Reuse

Entities (pages) can be **created and managed independently** from FLeT execution. The `cache_id` can be obtained upfront and reused across multiple operations:

```python
# 1. Create entity first (or lookup existing)
entity_result = entity_service.create(namespace='my-app', 
                                       request=Schema__Entity__Create__Request(cache_key='my-page'))
cache_id = entity_result.cache_id

# 2. Store cache_id for later use (e.g., in database, session, URL)
# 3. Later, trigger FLeT operations using the resolved cache_id
execute_service.execute_to_cache(namespace='my-app', cache_id=cache_id, request=html_request)

# 4. Even later, retrieve or run different FLeTs on the same entity
flows_service.list_flets(namespace='my-app', cache_id=cache_id)
```

This separation enables:
- **Decoupled workflows**: Entity creation in one service, FLeT execution in another
- **Entity reuse**: Same `cache_id` can be used across multiple FLeT operations
- **Pre-registration**: Create entities before HTML is available (e.g., job queues)
- **External tracking**: Store `cache_id` in databases, URLs, or external systems

### 8.3 FLeT Extensibility

Although the current implementation handles a simple use case (HTML store/retrieval), the architecture enables **independent creation and invocation of new FLeTs**:

- New FLeT actions can be added without modifying existing services
- New FLeT pipelines can compose existing actions
- Flow observability works automatically for any FLeT
- Routes can expose new FLeTs with minimal wiring

This will be leveraged in future phases to build more sophisticated HTML processing pipelines.

### 8.4 Testing Without Mocks

Using real objects via `create_html_cache_client()` proved highly effective:
- Tests run fast (in-memory cache)
- Tests catch real integration issues
- No mock maintenance overhead
- Tests serve as documentation

### 8.5 Type_Safe Auto-Creation

Type_Safe's automatic object creation simplifies service initialization:

```python
class FLeT__Html__Domain__Service(Type_Safe):
    cache_client    : Html_Cache__Client
    entity_service  : Cache__Entity__Service     # Auto-created if not provided
    execute_service : FLeT__Html__Execute__Service
    hash_generator  : Cache__Hash__Generator
```

### 8.6 Schema Import Paths

Established consistent pattern:
- `mgraph_ai_service_html_graph.schemas.cache.*` for cache schemas
- `mgraph_ai_service_html_graph.schemas.flet.*` for FLeT schemas
- `mgraph_ai_service_html_graph.service.cache.*` for services
